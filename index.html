Preface

This book began as reading notes. I wanted to point libFuzzer at a Linux kernel driver — not at a parser in user space, where every tutorial lives, but at code on the far side of a syscall: compiled by a different build system, instrumented by a different pass, and running in a context the fuzzer's own address space cannot see. The tutorials stop at that boundary. The papers assume you already know the engine. The engine itself is about ten thousand lines of C++ in compiler-rt/lib/fuzzer, and it turns out to answer the question directly if you sit down and read it.

The answer is the organising idea of this book, and it is almost disappointingly small: libFuzzer's coverage input is a byte array, and the engine cannot tell who filled it in. There is a linker section named __libfuzzer_extra_counters, added in March 2017 as “experimental support for user-provided coverage signal” (6ca44f91617d). Every non-zero byte in it becomes a coverage feature with exactly the standing of a byte the compiler's own instrumentation produced. Copy a KCOV ring buffer into that array and the feedback loop closes around a running kernel. The engine does not know. It does not need to know.

Everything else in these pages is either the machinery that makes that true, or the practical work of exploiting it.

Who this is for

  • You want to fuzz code your compiler never instrumented — a kernel, a firmware image, a binary you only have in object form — and you would rather understand the seam than copy a recipe.
  • You are looking for a first patch to LLVM or to Linux, and you want one with a real consumer rather than a TODO nobody is waiting on. Chapter 8 names files and lines.
  • You have typed -fsanitize=fuzzer and would like to know what the flag actually turned on. It is five things, not three, and the line of the clang driver that decides is quoted in §3.2.

You need C, enough C++ to read a template without flinching, and the habit of reading a diff and a stack trace. Part 2 additionally wants a Linux machine you can build a kernel on. No prior fuzzing experience is assumed: Chapter 1 builds the loop from nothing.

Part 1 is theory, and the four chapters are layers rather than topics — read them in order. Chapter 1 is the loop as its user sees it. Chapter 2 watches three other people smuggle coverage across the boundary described above, and extracts the one seam all three turn out to use. Chapter 7 installs the oracles that turn a silent corruption into an observable one. Chapter 8 is the list of gaps you could close upstream. Chapter 9 folds the hand-rolled harness into a small reusable layer, which is as close as this book comes to a victory lap.

If you came only for the kernel, the short path is Chapter 1, then §2.2 for the seam, then Chapter 6 for the lab — and then back to Chapters 3 and 4 the first time your harness does something you cannot explain. That moment arrives on schedule.

1.1 The core idea

libFuzzer is an in-process, coverage-guided, evolutionary fuzzing engine. Each word carries design weight:

  • In-process — the fuzzer and the code under test share one process. No fork/exec per input, so thousands of executions per second are possible; but the target must not exit(), leak global state, or crash the harness.
  • Coverage-guided — the target is instrumented at compile time by LLVM's SanitizerCoverage pass; the runtime observes which edges/features each input reaches.
  • Evolutionary — a corpus of inputs is mutated at random; any mutant that discovers new coverage is kept. Coverage is the fitness function.

Those three words are not slogans; each is a specific line of the engine. Here they are, in the order they act on one run:

List 1.1 FuzzerLoop.cpp:621 — in-process: the target is a direct function call 
RunningUserCallback = true;
int CBRes = CB(DataCopy, Size);   // ← your LLVMFuzzerTestOneInput, called in THIS process
RunningUserCallback = false;      //   no fork(), no IPC — that is where the speed comes from

…and where the fragility comes from: CB runs in the fuzzer's own address space, so a target that exit()s, aborts, or leaves a global dirty either kills the fuzzer or poisons the next input's run (§1.5). Speed and the "no persistent state" rule are the same fact.

List 1.2 FuzzerLoop.cpp:524 — coverage-guided: a run is scored by the new features it produces 
size_t NumUpdatesBefore = Corpus.NumFeatureUpdates();
TPC.CollectFeatures([&](uint32_t Feature) {              // walk every non-zero counter…
  if (Corpus.AddFeature(Feature, Size, Options.Shrink))  // …is this feature one no input had?
    UniqFeatureSetTmp.push_back(Feature);
});
size_t NumNewFeatures = Corpus.NumFeatureUpdates() - NumUpdatesBefore;   // the run's score

The "guidance" is that subtraction: how many features this input added that no earlier one had (§1.6). Coverage is not a metric printed and forgotten — it is the number the loop optimizes.

List 1.3 FuzzerLoop.cpp:730,538 — evolutionary: choose a survivor, mutate, keep only if it scored 
auto &II = Corpus.ChooseUnitToMutate(MD.GetRand());     // pick a parent from the corpus
// … MutateAndTestOne() mutates it (§1.7) and calls RunOne() …
if (NumNewFeatures || ForceAddToCorpus)                  // did the mutant find something new?
  Corpus.AddToCorpus({Data, Data + Size}, NumNewFeatures, …);   // if so, it becomes a parent too

That one if is the entire selection pressure: an input enters the corpus only if it produced a new feature, and the corpus is exactly the pool future mutations are drawn from. "Coverage is the fitness function" is not a metaphor — it is this branch.

Everything hangs off one user-provided function:

List 1.4 the entire contract — the one function you have to write 
extern "C" int LLVMFuzzerTestOneInput(const uint8_t *Data, size_t Size) {
  DoSomethingInterestingWithMyAPI(Data, Size);
  return 0;   // return -1 to reject this input from the corpus
}

Build with clang++ -g -O1 -fsanitize=fuzzer,address target.cc — the fuzzer component both instruments the code and links in libFuzzer's main(). Run it with a corpus directory, and read the stat lines: cov: is covered edges, ft: is features (edges + counters + value profiles + indirect-call pairs combined — the real currency of the search), NEW/REDUCE mark corpus growth and shrinkage.

Put those three words together and you get one loop — the whole engine on a single page:

Every box is a function you can now open in source: ChooseUnitToMutate/Mutate (§1.7), CB(Data, Size) inside ExecuteCallback (§1.5), CollectFeatures (§1.6), and the AddToCorpus that closes the loop only for an input that scored a new feature. The loop never stops; the corpus only grows toward code it has not yet reached.

Why libFuzzer exists: the problem it solved

Before coverage guidance, a fuzzer was blind: throw random bytes and hope. Past the first length field or magic-number check, random bytes almost never reach deeper code, so a blind fuzzer plateaus inside the input parser. AFL (Michał Zalewski, ~2013) broke that plateau: instrument the target at compile time and keep any input that reaches a new edge — a genetic loop with coverage as the fitness function. But AFL runs the target out of process (a fork per input via its fork server), which caps throughput at thousands per second.

libFuzzer (Kostya Serebryany, 2015) made the two moves that define it. (1) Run the target in-process — the direct CB(Data, Size) call in the loop above, no fork — for 100–1000× more executions per second. (2) Reuse the toolchain: the compiler already had SanitizerCoverage (built for the sanitizers) and ASan/MSan/UBSan (the bug oracle), so libFuzzer bolted onto those instead of shipping its own instrumentation pass and crash detector. The payoff — hundreds of thousands of exec/sec, a bug oracle in the same binary, and coverage any tool can read — is why libFuzzer became the engine behind Google's OSS-Fuzz, and why the same SanitizerCoverage now also feeds the kernel's KCOV (§1.9, Chapter 2).

How it evolved

None of this arrived at once. libFuzzer was created in January 2015 with a different target signature (void TestOneInput), no dedicated instrumentation pass of its own, and none of the four optional hooks of §1.3; the engine you just read about is the result of about a thousand commits, two complete replacements of the instrumentation it consumes, and at least one well-documented failed experiment. Because knowing which design decisions are load-bearing matters more than memorising them, the whole arc gets its own section: §1.10 lays out twelve years in six acts, with the commit behind every change. 1.5 ExecuteCallback: one run under the microscope

This is the single most instructive function in the runtime — every documented rule about fuzz targets ("tolerate any input", "don't modify the buffer", "be deterministic") is mechanically enforced or measured here:

List 1.9 compiler-rt/lib/fuzzer/FuzzerLoop.cpp:597 — ExecuteCallback: the heap copy that makes overflows in the input itself detectable 
ATTRIBUTE_NOINLINE bool Fuzzer::ExecuteCallback(const uint8_t *Data,
                                                size_t Size) {
  TPC.RecordInitialStack();
  TotalNumberOfRuns++;
  assert(InFuzzingThread());
  // We copy the contents of Unit into a separate heap buffer
  // so that we reliably find buffer overflows in it.
  uint8_t *DataCopy = new uint8_t[Size];
  if (Size)
    memcpy(DataCopy, Data, Size);
  if (EF->__msan_unpoison)
    EF->__msan_unpoison(DataCopy, Size);
  ...
  {
    ScopedEnableMsanInterceptorChecks S;
    AllocTracer.Start(Options.TraceMalloc);        // count mallocs/frees
    UnitStartTime = system_clock::now();           // per-unit timeout
    TPC.ResetMaps();                               // zero coverage counters
    RunningUserCallback = true;
    CBRes = CB(DataCopy, Size);                    // ← your target runs here
    RunningUserCallback = false;
    UnitStopTime = system_clock::now();
    assert(CBRes == 0 || CBRes == -1);             // "values other than 0/-1 reserved"
    HasMoreMallocsThanFrees = AllocTracer.Stop();  // cheap leak heuristic
  }
  if (!LooseMemeq(DataCopy, Data, Size))
    CrashOnOverwrittenData();                      // target must not write to input
  CurrentUnitSize = 0;
  delete[] DataCopy;
  return CBRes == 0;
}

Observations worth internalizing:

  • Fresh heap copy per run. The input is copied to a new heap allocation so ASan redzones sit immediately past Data[Size-1] — a one-byte overread becomes a hard crash instead of silently reading corpus memory.
  • TPC.ResetMaps() right before the call. Coverage counters are zeroed per-run; whatever the callback touches is attributed to exactly this input. This is the runtime half of the SanitizerCoverage handshake (§1.9).
  • Leak detection is a two-phase heuristic. Malloc/free counting is nearly free; only on imbalance does the engine escalate to a full (expensive) LeakSanitizer pass.
  • The docs' rules are asserts. Return value ∈ {0, −1}, input buffer immutable, run time and RSS bounded — each documented rule has a concrete enforcement point.

A feature is a 32-bit integer naming one observation: an edge paired with a hit-count bucket, or a value-profile bit, or an indirect caller/callee pair, or the run's stack depth. The exact encoding — and the fact that all four kinds share one numbering that shifts when a module appears — is §4.2; for now, treat a feature as "something this input did that is worth remembering." Corpus.AddFeature also implements input reduction: if a smaller input reaches an already-known feature, it can replace the bigger holder — that's the REDUCE event in the output log (§4.3). Note the doc's "return −1 to reject an input" lands here: a rejected input's coverage is never even collected.

1.7 MutateAndTestOne: the evolutionary step

List 1.11 compiler-rt/lib/fuzzer/FuzzerLoop.cpp:727 — MutateAndTestOne: one parent, up to MutateDepth mutants 
void Fuzzer::MutateAndTestOne() {
  MD.StartMutationSequence();
  auto &II = Corpus.ChooseUnitToMutate(MD.GetRand());  // weighted "energy" pick
  if (Options.DoCrossOver)
    MD.SetCrossOverWith(&Corpus.ChooseUnitToCrossOverWith(...).U);

  for (int i = 0; i < Options.MutateDepth; i++) {      // several mutations per pick
    size_t NewSize = 0;

      NewSize = MD.MutateWithMask(...);                // DFSan-guided byte mask
    if (!NewSize)
      NewSize = MD.Mutate(CurrentUnitData, Size, CurrentMaxMutationLen);

    bool NewCov = RunOne(CurrentUnitData, Size, /*MayDeleteFile=*/true, &II,
                         /*ForceAddToCorpus*/ false, &FoundUniqFeatures);
    if (NewCov) {
      ReportNewCoverage(&II, {CurrentUnitData, CurrentUnitData + Size});
      break;  // We will mutate this input more in the next rounds.
    }
  }
  II.NeedsEnergyUpdate = true;                         // entropic scheduling
}

Three things to notice:

  • Selection is weighted, not uniform. ChooseUnitToMutate uses the entropic power schedule (the "Running with entropic power schedule" banner in the output) — inputs whose features are rare get more mutation energy.
  • Mutations stack. Up to MutateDepth (default 5) mutations are applied cumulatively to one base unit before reselecting — the MS: 3 CrossOver-ChangeBit-CrossOver- trailer in NEW lines is this sequence.
  • MutateWithMask is where DFSan dataflow traces (from dataflow/DataFlow.cpp, §1.8) focus mutations onto exactly the input bytes that the "focus function" actually depends on.

The engine never disassembles anything; all coverage arrives through compiler-inserted instrumentation that FuzzerTracePC.cpp backs — and, importantly, the primary signal is not a callback at all but an inline counter increment. The layering mirrors kernel fuzzing exactly, which is why studying both sides pays off:

KCOV in the kernel is built on the same -fsanitize-coverage instrumentation; the kernel supplies its own callback implementations that write into a per-task ring buffer instead of libFuzzer's counter arrays. KCOV_TRACE_CMP is the kernel's counterpart of trace-cmp, consumed by syzkaller the same way libFuzzer's TORC consumes compare operands. Extending the callback family on the compiler side — as the proposed trace-args/trace-ret modes do (llvm/llvm-project#201410, §8.3) — creates new dataflow signals that any of these consumers — libFuzzer, Centipede, a KCOV-style ring buffer — can choose to collect.

1.10 Twelve years of libFuzzer, in six acts

Everything this chapter described was assembled, usually one commit at a time, and several of the pieces replaced earlier pieces that did not work. Reading that history is the fastest way to tell a load-bearing design decision from an accident — and the only way to know which advice in older blog posts is now wrong. Every row below is a commit in this repository (git log --oneline --stat compiler-rt/lib/fuzzer llvm/lib/Fuzzer — 754 commits before the 2017 move, 546 after).

The six acts

  • I · 2015 — a library, not a tool. In-process fuzzing on top of somebody else's coverage.
  • II · 2015–2016 — the ABI settles. One C function grows a return value and four optional hooks.
  • III · 2016 — the engine learns to read data. Value profile and TORC; coverage stops being only control flow.
  • IV · 2017 — the instrumentation is replaced, twice. Callbacks become inline counters; libFuzzer moves to compiler-rt.
  • V · 2018–2020 — scheduling, isolation, and one failed experiment. Entropic in, weighted mutation out, -fork arrives.
  • VI · 2021–2026 — maintenance, which is not the same as frozen.

Status note, stated precisely. Four patterns worth stealing from this history.
  • Weak symbols let an ABI grow. Four of the five entrypoints in §1.3 were added after release, and no existing target ever had to change.
  • Signals get tuned, not deleted. Stack depth was made coarser twice rather than removed; len_control was rewritten three times before becoming a default.
  • Second attempts work. -use_traces failed and came back as the TORC; the "tokens" experiment failed and came back as AFL dictionaries.
  • Smart mutation lost, smart selection won. Weighted mutator choice was reverted in 2018; energy-based seed choice shipped by default in 2020. Same ambition, opposite layer.

Chapter 2

Field studies: carrying coverage across a boundary the engine can't see

Chapter 1 dissected libFuzzer as it ships. Chapter 2 reads three real-world write-ups that push the engine somewhere it was never designed to go — the inside of an operating-system kernel — and asks a single question a compiler student should be able to answer by the end: if the fuzzing engine can only see a plain array of bytes, what exactly does the compiler have to produce, and who is allowed to fill that array?

Learning objectives

  • Explain the __libfuzzer_extra_counters linker section and why it lets non-instrumented code (a kernel, a rewritten binary) donate coverage to libFuzzer.
  • Trace how three independent projects — an AFL shim, a KCOV+libFuzzer harness, and a macOS binary rewriter — all reduce to "fill a byte array, then let CollectFeatures do its job."
  • Distinguish basic-block, edge, path, and data-flow coverage, and state precisely why SanitizerCoverage's "edge" mode is really enhanced block coverage.
  • Read a compiler callback (__sanitizer_cov_trace_pc, __sanitizer_cov_trace_cmp*) and say which fuzzing signal it feeds.

2.1 Why these two documents are on the syllabus

The two source documents are:

  • 2019“A gentle introduction to Linux Kernel fuzzing” (Marek Majkowski, Cloudflare). Drives the Linux netlink stack with AFL, feeding it coverage extracted from the kernel's KCOV facility through a shim that impersonates an AFL-instrumented binary.
  • 2024“Structure-Aware Linux Kernel Fuzzing with libFuzzer” and “Pishi: coverage-guided macOS KEXT fuzzing” (r00tkitsmm). The first feeds KCOV into libFuzzer and adds structure via libprotobuf-mutator; the second invents coverage from scratch on a closed-source Apple kernel by rewriting the binary, then feeds that into libFuzzer.

Read together they form a natural progression — same target class, three different engines, one shared trick — which is exactly why they make a good capstone for the material in Chapter 1.

A note on why the kernel is hard. Everything in Chapter 1 assumed in-process fuzzing: the engine and the code under test share an address space, so coverage counters are just global variables the callback happens to touch. A kernel does not live in your fuzzer's address space. The coverage is produced on the other side of a system-call boundary, in a different privilege level. All three case studies are, at heart, solutions to one plumbing problem: how do I move a coverage signal from where it is produced to the byte array the engine reads?

2.2 The linker seam: __libfuzzer_extra_counters

Before the case studies, we need the one runtime feature they all stand on. In §1.6 we saw TPC.CollectFeatures walk the instrumented 8-bit counter regions that SanitizerCoverage emits. What Chapter 1 did not show is that the very same loop also walks a second array — one that the compiler never fills, that you fill:

The seam is deliberate, and datable. It is not a linker accident: 6ca44f91617d (2017-03), "create experimental support for user-provided coverage signal", added exactly this array. Every client in this chapter — the AFL/KCOV shim (§2.3), the KCOV harness (§2.4), Pishi (§2.5) — is a consumer of that one commit.

Definition — extra coverage counters. A user-declared byte array placed, via a compiler attribute, into a specially named linker section (__libfuzzer_extra_counters). libFuzzer treats every non-zero byte in it as a coverage feature, identical in status to a byte the compiler's own instrumentation would have produced. You declare it like this: List 2.2 declaring extra counters: a byte array in a magic linker section 
__attribute__((section("__libfuzzer_extra_counters")))
unsigned char libfuzzer_coverage[32 << 10];   // 32 KiB of hit counters

Here is the payoff, and it is worth reading slowly. In §1.6, CollectFeatures appended features from the instrumented modules. Two lines later in the same function it does this:

size_t FirstFeature = 0;
for (each instrumented module region)          // ← compiler-emitted 8-bit counters
  FirstFeature += 8 * ForEachNonZeroByte(Region.Start, Region.Stop,
                                         FirstFeature, Handle8bitCounter);

                           FirstFeature, Handle8bitCounter);

That marked block is the whole seam. The engine does not care whether a non-zero byte was written by compiler-inserted instrumentation or by a hand-written loop that copied numbers out of a kernel. Both go through Handle8bitCounter, both become features, both drive the corpus decisions from §1.6, and both get zeroed by ClearExtraCounters() inside ResetMaps() before the next run. A kernel fuzzer, then, needs to accomplish exactly one thing per execution: translate whatever the kernel recorded into non-zero bytes in that array.

First-time-contributor note — the __start_/__stop_ trick. When you place data in a section called foo, the GNU/LLVM linker automatically synthesizes two symbols, __start_foo and __stop_foo, pointing at the first byte and one-past-the-last byte of everything gathered into that section. This is how a library can find an array that user code defined, without any registration call — the same mechanism SanitizerCoverage itself uses for its counter and PC tables (__start___sancov_cntrs, etc.). The weak attribute means "don't error if nobody created this section"; the range simply comes back empty. If you ever add a new instrumentation table to the compiler, this is the ABI pattern you will copy.
Foreshadowing Pishi. Note the file above is guarded to Linux and friends. On Darwin the story is different — hold that thought until §2.5, where the one-line stub FuzzerExtraCountersDarwin.cpp forces the macOS author to patch LLVM itself.

2.3 Case study A — tricking AFL with KCOV (Cloudflare, 2019)

referencelibfuzzer-kcov.html · engine: AFL · transport: KCOV ring buffer → AFL shared memory

This is the oldest and, pedagogically, the cleanest of the three, because AFL's coverage interface is even simpler than libFuzzer's. AFL shares a 64 KiB array of 8-bit counters with the target — the file calls it trace_bits or shared_mem — where each byte is a hit counter for one (branch_source, branch_dest) edge. An AFL-instrumented compiler emits, at every branch, code equivalent to:

List 2.4 AFL's classic edge-hashing scheme (from the Cloudflare post) 
cur_location = <COMPILE_TIME_RANDOM>;              // a random label per block
shared_mem[cur_location ^ prev_location]++;       // bump the edge's counter
prev_location = cur_location >> 1;                 // shift so A→B ≠ B→A
Why the random label and the shift? The XOR of two block labels identifies the edge, not the block, giving AFL edge coverage (see §2.6). Random labels spread edges uniformly across the 64 KiB table to minimise collisions. The >> 1 breaks the symmetry of XOR so that the edge A→B and the edge B→A hash to different buckets — without it, direction would be invisible.

The kernel, of course, was not compiled by afl-gcc, so those magic labels do not exist. What the kernel does offer is KCOV: enable it with an ioctl, run the code you care about, and a per-task ring buffer fills with the raw program counters (%rip values) of every basic block executed:

List 2.5 KCOV in KCOV_TRACE_PC mode — enable, exercise, read the ring buffer 
ioctl(kcov_fd, KCOV_ENABLE, KCOV_TRACE_PC);
/* ... exercise kernel code via a syscall ... */
ioctl(kcov_fd, KCOV_DISABLE, 0);
// kcov_ring[0] = count; kcov_ring[1..count] = PCs of executed blocks

The shim's job is to convert one coverage vocabulary into the other. It hashes each KCOV program counter into a 16-bit bucket and replays AFL's own edge formula, so a kernel PC trace ends up looking, to AFL, exactly like output from an AFL-instrumented binary:

List 2.6 the shim's translation: KCOV program counters into AFL's edge-hashed bitmap 
uint16_t prev_location = 0;
for (i = 0; i < n; i++) {
    uint16_t cur_location = hash_function(kcov_ring[i + 1]);  // PC → uniform label
    shared_mem[cur_location ^ prev_location]++;               // AFL's edge encoding
    prev_location = cur_location >> 1;
}

Around this sits a small fork-server loop that reads one test case from AFL, enables KCOV, pokes the kernel (in the post, by crafting a netlink message out of the input bytes), disables KCOV, fills shared_mem, and reports whether dmesg showed a fresh crash. The kernel runs under KVM via virtme so a bug does not take down the host.

The transferable lesson. A coverage-guided fuzzer's coupling to the target is astonishingly thin: a shared array of hit counters, plus a convention for how indices are computed. Once you accept that, "instrumentation" stops being magic. Anyone who can produce the indices — a compiler pass, a kernel facility, or a hand-written hash of raw PCs — can drive the fuzzer. Case studies B and C are the same lesson told with libFuzzer's array instead of AFL's.

2.4 Case study B — libFuzzer + KCOV, structure-aware (2024)

referencelibfuzzer-kcov.md (part 1) · engine: libFuzzer · transport: KCOV ring buffer → __libfuzzer_extra_counters

Now swap AFL for libFuzzer. Because of §2.2, there is no shim binary to fake and no 64 KiB protocol to imitate — you just declare the extra-counters array and fill it. The harness sets KCOV up once in LLVMFuzzerInitialize (recall §1.3: the optional startup hook), then brackets each unit with enable/collect/disable:

List 2.7 condensed from libfuzzer-kcov.md, part 1 — the one-time KCOV setup in LLVMFuzzerInitialize 
__attribute__((section("__libfuzzer_extra_counters")))

  kcov = open("/sys/kernel/debug/kcov", O_RDWR);
  ioctl(kcov, KCOV_INIT_TRACE, KCOV_COVER_SIZE);    // KCOV_INIT_TRACE — there is no …_TRACE64

Compare the marked line with §2.3's shared_mem[...]++. It is the identical idea — hash a kernel PC into a slot and bump it — but now the array is the one CollectFeatures reads directly (§2.2), so the fuzzer needs no impersonation. libFuzzer clears the array for you each run via ClearExtraCounters().

Two refinements a compiler student should notice

(1) Comparison coverage from the kernel. The kernel config in the post enables KCOV_ENABLE_COMPARISONS. This is the kernel's counterpart of the compiler's -fsanitize-coverage=trace-cmp from §1.9: instead of (or in addition to) block PCs, KCOV can record the operands of comparison instructions. Feed those to libFuzzer's value-profile / table-of-recent-compares machinery and the fuzzer gains the same "gradient toward passing a comparison" superpower it has for user-space targets. Same concept, produced by KCOV instead of by __sanitizer_cov_trace_cmp*.

(2) Structure-aware input via libprotobuf-mutator. Kernel APIs are stateful — you cannot feed a raw byte blob to a syscall sequence and expect to get deep. The post uses libprotobuf-mutator (LPM) and the DEFINE_PROTO_FUZZER macro, so the fuzzer mutates a typed protobuf message (a description of syscalls and their arguments) rather than bytes, and LPM serialises it into the input. This is the same "custom mutator" seam from §1.3 (LLVMFuzzerCustomMutator), just wrapped in a library.

The KASAN → SIGSEGV patch, and why it is necessary. Recall from §1.5 that libFuzzer only preserves the offending input and stops when the run crashes with a signal. But a kernel bug caught by KASAN merely prints a report to dmesg; from the userspace harness's point of view the syscall just returns and the loop continues — the guilty input is mutated away and lost. The author's fix is to patch the kernel's print_error_description() in mm/kasan/report.c to send_sig_info(SIGSEGV, …, current), delivering a signal to the very task that triggered the bug. Now the crash lands inside the harness process, ExecuteCallback's signal handler fires, and the reproducer is saved. This is a beautiful illustration of a §1.5 invariant — "a bug is only a bug if it reaches the engine as a signal on the fuzzing thread" — being enforced by editing the target rather than the engine.

2.5 Case study C — Pishi: coverage without source (macOS, 2024)

referencelibfuzzer-kcov.md (part 2) · engine: libFuzzer · transport: static binary rewriting → _sanitizer_cov_trace_pc → shared memory → extra counters

Case studies A and B both had a cooperating target: the kernel came with KCOV because it was compiled from source with the right flags. Pishi asks the hardest version of the question — what if you have no source and no coverage facility at all? The target is a closed-source Apple kernel extension (KEXT); you cannot recompile it, and Apple Silicon offers no kernel debugger. There is nothing for -fsanitize-coverage to instrument.

The answer is static binary rewriting: Pishi edits the compiled KEXT so that each basic block, when executed, calls a coverage-recording function. Because it cannot recompile, it must reproduce by hand what the compiler would have inserted. The mechanics are worth seeing because they make "instrumentation" concrete:

  1. Pre-fill the injected KEXT with many copies of a trampoline (using the assembler's .rept/.endr to spray them), each a slot able to save registers, call the coverage function, run one displaced instruction, and jump back.
  2. For every basic block, overwrite one instruction with a branch to a fresh trampoline. A key AArch64 insight the post leans on: all instructions are 32 bits and most are position-independent, so the displaced instruction can be relocated verbatim into the trampoline. (The post proves ~99.7% of "valuable" blocks are instrumentable this way.)
  3. The trampoline calls a hand-written _sanitizer_cov_trace_pc — the same symbol name the compiler would emit for -fsanitize-coverage=trace-pc — which records the block's address into a coverage buffer shared with the fuzzer.
List 2.8 Pishi's coverage sink — note the KCOV-shaped ring buffer 
void sanitizer_cov_trace_pc(uint16_t kext, uintptr_t address) {
  if (instrumented_thread == current_thread_id() && (targeted_kext & kext)) {
    unsigned long pos = coverage_area->kcov_pos;         // exactly KCOV's layout:
    coverage_area->kcov_area[pos] = address;             // [0]=count, [1..]=PCs
    coverage_area->kcov_pos += 1;
  }
}

Then, in the userspace fuzzer, the loop is identical in spirit to case study B — copy PCs from the shared buffer into the extra-counters array:

List 2.9 Pishi's userspace collector — ring-buffer PCs folded into the extra-counters array 
void pishi_collect() {
  for (int i = 0; i < coverage->kcov_pos; i++)
    _pishi_libfuzzer_coverage[coverage->kcov_area[i] % sizeof(_pishi_libfuzzer_coverage)]++;
}
Where a compiler contributor actually gets pulled in. On Linux, §2.2 just works. On macOS it does not: the file FuzzerExtraCountersDarwin.cpp is a stub — uint8_t *ExtraCountersBegin() { return nullptr; } — so CollectFeatures finds an empty range and none of the Pishi coverage would count. The author's remedy is to modify LLVM's own compiler-rt and rebuild it, implementing the Darwin extra-counters section (the Mach-O equivalent of the __start_/__stop_ symbols from §2.2). This is the moment the project stops being "a fuzzing harness" and becomes "a patch to the toolchain" — precisely the kind of change a first-time compiler-rt contributor would send upstream.

And you would not be starting from nothing. The third sibling, FuzzerExtraCountersWindows.cpp, solves the identical problem on a platform that also lacks __start_/__stop_ symbols — by defining the bracketing symbols itself in a section whose name sorts just before the user's:

One platform implemented twice is the best possible specification for implementing it a third time.

Stateful reset by forking. An in-process loop leaks kernel state (open descriptors, mach ports, allocations) from one iteration into the next, poisoning the determinism §1.1 demanded. Pishi's answer for stateful targets is to fork() inside LLVMFuzzerTestOneInput: the child enables coverage, runs the case, and exits (letting the OS reclaim its resources); the parent waits and harvests coverage from the shared buffer. Each iteration then starts from a semi-fresh kernel state. The same problem is why syzkaller and others go to such lengths for a clean slate per execution.

2.6 A compiler's taxonomy of coverage

All three case studies chose basic-block coverage because raw PCs are what KCOV and a binary rewriter can cheaply produce. But a compiler contributor should know the full ladder, because each rung is a different amount of work in the instrumentation pass, and the Pishi write-up spends real effort on the distinctions.

Definition — control-flow graph. The basic blocks (maximal straight-line instruction runs with no branch in except at the top and none out except at the bottom) are the nodes; branches are the edges; a path is a route through the graph. Coverage metrics differ in which of these they can distinguish.
Table 2.1 The coverage ladder from block to path, and what each rung can distinguish that the one below it cannot.
MetricWhat it recordsDistinguishes…Cost / caveat
Blockwhich nodes executed reaching a block vs not cheapest; blind to order and to which edge was taken
Edgewhich node→node transitions executed A→B→C from A→C→B (see AFL quote below) needs edge identity; "critical edges" must be split first
Pathwhole routes through the CFG every distinct execution history most precise; suffers path explosion — usually impractical
Data-flowwhich input bytes reach which operations / comparisons how close a value came to a target trace-cmp, value profile, DFSan; the §1.9 "gradient" signals

Why edge beats block is the single most important idea here, and the AFL technical paper (quoted in the Pishi post) states it best:

List 2.11 the AFL paper's example: two different control flows, identical block coverage 
  A -> B -> C -> D -> E   (edges: AB, BC, CD, DE)
  A -> B -> D -> C -> E   (edges: AB, BD, DC, CE)

Both executions cover the same blocks {A,B,C,D,E}, so block coverage cannot tell them apart — yet they are different control flows, and "security vulnerabilities are more often associated with unexpected state transitions than with merely reaching a new block."

Critical edges, and the honest caveat about "edge" coverage

SanitizerCoverage claims edge coverage, and it earns part of that claim by splitting critical edges. A critical edge is one that is neither the only edge leaving its source nor the only edge entering its destination; on such an edge you cannot tell, from block counts alone, whether it was taken. The compiler inserts a synthetic empty block on the edge and instruments that:

List 2.12 a critical edge, and the dummy block the compiler instruments in its place 
void foo(int *a) {
  if (a) { *a = 0; }
  else   { /* compiler inserts a dummy block here, then instruments it */ }
}
The nuance the Pishi author is careful to make (via ColLAFL). Splitting critical edges is not the same as true edge coverage. Even with no critical edges present, two paths can share every block yet differ in which edges they used, and SanitizerCoverage's block-plus-split-edge instrumentation will report them identically. So what Clang labels "edge coverage" is best described as enhanced block coverage: strictly more information than plain blocks, strictly less than genuine edge tracking. For a student this is the difference between believing documentation and reading the pass — and it is exactly the sort of subtlety worth confirming in llvm/lib/Transforms/Instrumentation/SanitizerCoverage.cpp yourself.

Compare shattering — turning one hard comparison into four easy ones

The last rung, data-flow, is where the compiler helps the fuzzer defeat "magic value" checks. A 32-bit equality is a wall: random mutation guesses it with probability 2⁻³². The trick (compare shattering / sub-instruction profiling, §1.9's trace-cmp) is to let the instrumentation observe the comparison byte-by-byte, so the fuzzer gets partial credit for each correct byte:

Case study B gets this from the kernel for free by turning on KCOV_ENABLE_COMPARISONS.

3.2 The compiler's menu (SanitizerCoverage.rst)

-fsanitize-coverage= is not one feature but a menu of independent instrumentation kinds, each defined by the callback(s) the compiler inserts and the runtime must define. Meaning lives entirely in whoever implements the callback (libFuzzer, a kernel, AFL, your own tool).

Trace handlers — the data-flow signals

All of the comparison callbacks funnel into one function. Read it closely — it is doing two different jobs at once:

List 3.4 compiler-rt/lib/fuzzer/FuzzerTracePC.cpp:356 — HandleCmp, which does two jobs per comparison 
template <class T>
void TracePC::HandleCmp(uintptr_t PC, T Arg1, T Arg2) {
  uint64_t ArgXor = Arg1 ^ Arg2;
  if (sizeof(T) == 4)      TORC4.Insert(ArgXor, Arg1, Arg2);   // job 1: remember the operands
  else if (sizeof(T) == 8) TORC8.Insert(ArgXor, Arg1, Arg2);
  uint64_t HammingDistance = Popcountll(ArgXor);                        // bits that differ
  uint64_t AbsoluteDistance = (Arg1 == Arg2 ? 0 : Clzll(Arg1 - Arg2) + 1);
  ValueProfileMap.AddValue(PC * 128 + HammingDistance);       // job 2: "how close" as coverage
  ValueProfileMap.AddValue(PC * 128 + 64 + AbsoluteDistance);
}
  • Job 1 — TORC (Table Of Recent Compares). The raw operands (Arg1, Arg2) are stashed, keyed by their XOR. §3.4 shows the mutator drawing from this table to splice a wanted constant straight into the input. This is what actually solves x == 0xCAFEF00D.
  • Job 2 — value profile. Two numbers — how many bits differ (HammingDistance) and the magnitude of the gap (AbsoluteDistance) — are folded with the PC into a bitset. Each newly-set bit is a new feature, so an input that gets closer to satisfying the compare is rewarded even before it matches. This is the "gradient" from §1.9/§2.6, and it only counts when -use_value_profile=1.

3.4 Closing the loop: TORC → mutation

We now have half a cycle: the compiler emits trace_cmp, and HandleCmp files the operands in TORC. Here are the two pieces we have so far only named — the table, and the one function that fills it:

List 3.5 compiler-rt/lib/fuzzer/FuzzerTracePC.h:30,105 — the TORC is three small fixed-size tables 
template<class T, size_t kSizeT>
struct TableOfRecentCompares {           // "TORC"
  static const size_t kSize = kSizeT;    // 32 entries per table
  struct Pair { T A, B; };
  void Insert(size_t Idx, const T &Arg1, const T &Arg2) {
    Idx = Idx % kSize;                   // ring buffer: newest overwrites oldest
    Table[Idx].A = Arg1; Table[Idx].B = Arg2;
  }
  Pair Get(size_t I) { return Table[I % kSize]; }
  Pair Table[kSize];
};
// one table per operand width — that is the whole "memory" of the compare engine:
TableOfRecentCompares<uint32_t, 32> TORC4;
TableOfRecentCompares<uint64_t, 32> TORC8;
TableOfRecentCompares<Word,     32> TORCW;   // memcmp / strcmp byte-strings
List 3.6 compiler-rt/lib/fuzzer/FuzzerTracePC.cpp:356 — HandleCmp, called from every __sanitizer_cov_trace_cmp* (§3.3) 
template <class T>
void TracePC::HandleCmp(uintptr_t PC, T Arg1, T Arg2) {
  uint64_t ArgXor = Arg1 ^ Arg2;
  if (sizeof(T) == 4)      TORC4.Insert(ArgXor, Arg1, Arg2);   // remember the operands
  else if (sizeof(T) == 8) TORC8.Insert(ArgXor, Arg1, Arg2);
  uint64_t HammingDistance  = Popcountll(ArgXor);                       // [0,64]: how many bits differ
  uint64_t AbsoluteDistance = (Arg1 == Arg2 ? 0 : Clzll(Arg1 - Arg2) + 1);
  ValueProfileMap.AddValue(PC * 128 + HammingDistance);        // value profile: a "closeness" gradient
  ValueProfileMap.AddValue(PC * 128 + 64 + AbsoluteDistance);
}

Two independent things happen at every comparison. (1) The operands are dropped into the ring-buffer TORC — at index (Arg1 ^ Arg2) % 32, so the slot is chosen by the operand pair and not by the compare site: two different ifs that compare the same values collide, and the same if with different operands lands elsewhere. With 32 slots per width, the table is a short-term memory of recent values, not a per-branch record — which is all the mutator needs to splice one back verbatim. (2) Their distance (how many bits differ, HammingDistance; and how far apart numerically, AbsoluteDistance) is folded into the value profile: the gradient that lets -use_value_profile=1 reward an input for getting closer to satisfying a check even before it passes (§3.3). Note the function is ALWAYS_INLINE and ATTRIBUTE_NO_SANITIZE_ALL — it sits on the hottest path in the program, so it must be tiny and must not be instrumented by its own coverage pass.

Both halves are datable. The value profile — "treats new values as new coverage" — landed in d46a59fac459 (2016-08); the compare table it sits beside, -trace_cmp / TableOfRecentCompares, in a5f94fb6c9cb (2016-10). Together they are what turned libFuzzer from an edge-counter into something that can reason about data (§3.3).

The other half is in the mutator, and it is what makes the whole scheme more than a passive metric. First, the per-run reset that keeps signals attributed to the right input:

3.7 The mutation engine, and what its git history reveals

FuzzerMutate.cpp is where the "evolutionary" in "coverage-guided evolutionary fuzzing" actually lives. §1.7 showed when mutation happens (MutateAndTestOne); §3.4 showed the feedback that steers it (TORC). This section opens the engine itself — the palette of transformations, the scheduler that picks among them, and what the file's real commit history (git log compiler-rt/lib/fuzzer/FuzzerMutate.cpp) teaches about how much "intelligence" belongs in the mutator versus the feedback.

The scheduler is deliberately dumb

Given the palette, how does the engine choose? It does not weight, rank, or learn — it picks uniformly at random and retries if the pick fails to apply:

List 3.11 compiler-rt/lib/fuzzer/FuzzerMutate.cpp:541 — MutateImpl — one uniform-random mutator per round, retried if it declines 
for (int Iter = 0; Iter < 100; Iter++) {
  auto M = Mutators[Rand(Mutators.size())];        // uniform random pick
  size_t NewSize = (this->*(M.Fn))(Data, Size, MaxSize);
  if (NewSize && NewSize <= MaxSize) {              // a mutator returns 0 when it can't apply
    CurrentMutatorSequence.push_back(M);           //   (e.g. InsertByte at MaxSize)
    return NewSize;                                //   — so we just try another
  }
}
*Data = ' '; return 1;                             // fallback; should be rare

That 100-try retry loop is the only cleverness: mutations "fail" (return 0) when they cannot apply to the current buffer, and the engine simply rolls again rather than wasting the run. The choice of which transformation is pure chance.

The git history's biggest lesson: smart scheduling was tried, and reverted. Reading git log --oneline compiler-rt/lib/fuzzer/FuzzerMutate.cpp past the NFC churn, three commits carry the real story of where "intelligence" belongs:
  • Weighted scheduling — added, then removed. "Initial implementation of weighted mutation leveraging during runtime" (5a9baa330caf, 2018) made mutator selection favour transformations that had historically produced new coverage. It was later ripped out — "Remove mutation stats and weighted mutation selection" (8c95b48ba273). The engine settled back to the uniform pick above. The lesson the maintainers encoded: the intelligence that makes fuzzing work is in the feedback (coverage + TORC, §3.3–§3.4), not in guessing which bit to flip. A dumb mutator plus a smart fitness function beats a smart mutator.
  • Data-flow-guided mutation — the one "smart" mutator that stayed, opt-in. "first experimental attempt at DFT-based mutations (DFT = data-flow-trace)" (6b87e0c18f04, 2018) added MutateWithMask (§1.7): mutate only the input bytes a focus function actually depends on, learned from DFSan traces (§1.8). It is the closest the engine comes to targeted mutation — and it is off by default, falling back to the dumb path when the mask is empty (9d5e7ee29665 "Fallback to default Mutate when MutateWithMask fails").
  • Sanitizer-interaction care. "Fix MSan false positives with custom mutators" (423024904825, 2021) added the __msan_unpoison calls around the custom-mutator call (§3.8) — because a user's mutator writing into a buffer would otherwise trip MemorySanitizer's uninitialized-read checks. Small commit, real correctness.
(And "Refactor mutation strategies into a standalone library" was proposed and reverted three times — c4a41cd77c15, 361f742f168d — so the engine still resists clean extraction.)
The ABI itself has a history too. §3.5 read the clang-fuzzer log; its first commit (git show 667c152bce2a, 2015) is a time capsule of the pre-standard interface — the target was extern "C" void TestOneInput(uint8_t*, size_t), with no LLVMFuzzer prefix and a void return. The rename to LLVMFuzzerTestOneInput and the change to an int return (e39fec5b0664, "make LLVMFuzzerTestOneInput return int instead of void") is what gave the return value its meaning — 0 accept, −1 reject (§1.6). The one-function contract of §1.3 was not born finished; it grew the semantics we now rely on.

Is there a “havoc” mode? libFuzzer vs AFL

Readers coming from AFL, AFL++, or LibAFL ask where libFuzzer's havoc stage is. The honest answer: there isn't one — the word appears nowhere in libFuzzer's source or docs. Those tools use a two-phase model: a deterministic stage (a systematic walk of single-bit flips, byte arithmetic, and a fixed table of “interesting” values like 0, 0xFFFF, INT_MAX), followed by havoc — an aggressive stage that stacks a random number of mutations (AFL: 1–128) onto a seed and tests the result once. libFuzzer has neither phase. It never does the deterministic walk, and it has no separate stacked-burst mode. It has exactly one behaviour: the uniform-random pick from the palette above (§3.7), applied in a short, tested chain.

That chain is the closest analogue to havoc, and it is worth seeing precisely, because it is far more conservative than a havoc burst. MutateAndTestOne mutates the chosen seed up to MutateDepth times — but it re-runs the target after every single mutation and stops early the moment one earns new coverage:

List 3.12 compiler-rt/lib/fuzzer/FuzzerLoop.cpp — MutateAndTestOne (condensed); FuzzerFlags.def: mutate_depth = 5 
for (int i = 0; i < Options.MutateDepth; i++) {          // default depth = 5, not 128
  size_t NewSize = MD.Mutate(CurrentUnitData, Size, CurrentMaxMutationLen);  // exactly ONE mutator
  Size = NewSize;
  bool NewCov = RunOne(CurrentUnitData, Size, /*…*/);     // test after EVERY mutation
  if (NewCov) break;   // "We will mutate this input more in the next rounds." (it re-enters the corpus)
}

So mutations do accumulate — the output of one Mutate() is the input to the next — but only up to five deep, and the loop bails as soon as it finds signal, handing the winning input back to the corpus to be mutated further next round (§3.6). This is the same philosophy as the “dumb scheduler” above: don't gamble on a big stacked transformation, take one small step, measure, and let the feedback loop decide whether to keep going.

So there is no static integer table. libFuzzer's ChangeBinaryInteger reads an integer out of the buffer and adds or subtracts a random value (sometimes byteswapping it); ChangeASCIIInteger parses a decimal run and increments, decrements, or doubles it. The specific magic constants a target needs don't come from a table at all — they arrive through AddWordFromTORC (recent comparison operands) and the dictionaries (§3.4). That is the whole thesis restated: constants worth trying are discovered from the program, not enumerated in advance.

The FuzzedDataProvider positional-fragility problem

There is a real effect the “havoc” framing is reaching for, and it is worth stating correctly. When a harness turns the raw byte array into structured choices with FuzzedDataProvider (FDP) — a parametric generator: the bytes are a script of pseudo-random decisions — libFuzzer's byte-level mutators still operate on the flat array, oblivious to the structure. Insert or delete a byte and you can shift what every following read decodes: a byte that was an array length is suddenly read as a boolean, and the generated object changes shape wholesale. That is genuine, and it is why incremental exploration of FDP-built inputs is harder than of a raw parser.

But FDP is not naïve about it. It splits the buffer by role: payload reads (ConsumeBytes) take from the front, while control reads (ConsumeIntegral, ConsumeIntegralInRange, ConsumeBool, ConsumeEnum) take from the back — a deliberate choice to keep a front-side edit from scrambling the branch-selecting integers:

List 3.13 compiler-rt/include/fuzzer/FuzzedDataProvider.h — ConsumeIntegralInRange, which eats bytes from the back so front offsets stay stable

So a one-byte insertion at the front shifts the payloads but leaves the back-consumed selectors comparatively stable — the cascade is blunted, not eliminated. The practical takeaway is the one this chapter keeps arriving at: when a target is genuinely structure-sensitive, don't fight the flat-array mutators — replace them with a structure-aware custom mutator (§3.8) or a typed grammar via libprotobuf-mutator (§2.4), which mutate the object instead of the bytes underneath it.

3.8 Custom mutators: replacing the palette, and the two golden rules

The dumb-scheduler design has a powerful consequence: because the mutator list is just data, you can replace it. The defaults do not vanish entirely, though: they are still reachable through one exported escape hatch, which is the key to writing a custom mutator that isn't hopeless.

LLVMFuzzerMutate runs the full default palette — bit-flips, integer nudges, dictionary and TORC splices — on whatever sub-buffer you hand it. So the pattern for a structured format is: you own the structure, and you delegate the leaf bytes to libFuzzer.

A worked example: a length-prefixed, checksummed packet

Consider a format that a naive fuzzer would flail against: byte 0 is a length prefix, the last byte is an XOR checksum, and the target rejects anything whose checksum doesn't match. Without help, the fuzzer spends ~all its runs on inputs the target throws away at the checksum gate. A custom mutator maintains the invariant from the inside:

List 3.16 a custom mutator that maintains the length prefix and checksum from the inside 
// Reuse libFuzzer's smarts:
extern "C" size_t LLVMFuzzerMutate(uint8_t *Data, size_t Size, size_t MaxSize);

extern "C" size_t LLVMFuzzerCustomMutator(uint8_t *Data, size_t Size,
                                          size_t MaxSize, unsigned int Seed) {
  if (Size < 2) return 0;                          // reject too-small inputs

  // Step 1: parse — byte 0 is a length prefix; the payload is the middle.
  size_t payload_size     = Size - 2;
  size_t max_payload_size = MaxSize - 2;            // leave room for prefix + checksum

  // Step 2: mutate ONLY the payload, with the default engine.
  size_t new_payload_size =
      LLVMFuzzerMutate(&Data[1], payload_size, max_payload_size);   // ← the escape hatch

  // Step 3: re-establish the invariant — recompute the checksum.
  uint8_t new_checksum = 0;
  for (size_t i = 1; i < 1 + new_payload_size; ++i) new_checksum ^= Data[i];
  Data[1 + new_payload_size] = new_checksum;

  return 1 + new_payload_size + 1;                  // prefix + payload + checksum
}

extern "C" int LLVMFuzzerTestOneInput(const uint8_t *Data, size_t Size) {
  // Every input that reaches here already has a valid checksum.
  return 0;
}

Compare this with §3.4. There, the trace-cmp loop cracks a magic constant from the outside, one operand at a time, by observing the failed compare. That is the right tool when you do not own the format. But when you do own it, a custom mutator is strictly better: it never generates an invalid packet in the first place, so 100% of runs exercise the code past the checksum instead of bouncing off it. Structure-aware fuzzing (the LPM/DEFINE_PROTO_FUZZER path from Chapter 1's kernel case study) is this idea scaled up to a full grammar.

Two golden rules for custom mutators

  • 1. Don't reinvent the wheel. Because your custom mutator is the only active mutator (the code above), the default bit-flipping is reachable only if you call LLVMFuzzerMutate on your leaf values (strings, integers, the payload). Let libFuzzer do the byte-level exploration; you do the structure. A custom mutator that hand-rolls its own byte-flips throws away years of tuned heuristics — and the TORC/dictionary splices that make coverage-guided fuzzing fast.
  • 2. Handle MaxSize strictly. libFuzzer shrinks the size budget during a run to find smaller inputs; if your mutator writes past MaxSize it is a real out-of-bounds write and the fuzzer crashes on itself. In the example, note max_payload_size = MaxSize - 2 — you must reserve room for every byte you add around the delegated region. (libFuzzer even auto-disables -len_control when it detects a custom mutator — FuzzerDriver.cpp:203, with an INFO: line — but MaxSize still varies via input reduction, so never assume it is constant.)
The crossover corollary. Notice CrossOver in the default palette (§3.7): it splices raw bytes from another corpus unit into the input, with zero understanding of your framing. It is reached through LLVMFuzzerMutate, so it can paste another packet's whole serialized form — its length prefix, payload, and checksum bytes — into the middle of your payload. For an opaque payload that is harmless (you recompute the checksum); for a nested structure it is corruption. That is why a custom mutator usually wants a companion LLVMFuzzerCustomCrossOver: defining it appends a structure-aware combiner to the active set (the third line of the swap code above), so the engine can merge two of your inputs at the level of your format instead of blind byte-splicing. Mutator and crossover are a pair — write both, or the only cross-pollination you get is the blind kind.

4.2 What exactly is a feature?

§1.6 called a feature "a 32-bit integer encoding (edge × counter-bucket)" and moved on. Here is the encoding, in full, from the two functions that implement it.

Step one: a hit count becomes one of eight buckets

List 4.1 compiler-rt/lib/fuzzer/FuzzerTracePC.h:213 — CounterToFeature: a hit count bucketed into one of eight features 
// Given a non-zero Counter returns a number in the range [0,7].
template<class T>
unsigned CounterToFeature(T Counter) {
    // Counter bucket: [1] [2] [3] [4-7] [8-15] [16-31] [32-127] [128+]
    // Feature number:  0   1   2    3     4       5       6       7
    //
    // This is a heuristic taken from AFL (see
    // http://lcamtuf.coredump.cx/afl/technical_details.txt).
    assert(Counter);
    unsigned Bit = 0;
    /**/ if (Counter >= 128) Bit = 7;
    else if (Counter >= 32)  Bit = 6;
    ...
    return Bit;
}

Eight log-ish buckets, inherited from AFL. This is the concrete reason §6.2's choice between Counters[Idx] = 1 and Counters[Idx]++ matters: with = 1 a kernel block can only ever produce bucket 0, so a loop that runs 3 times and a loop that runs 300 times are the same input to the engine. With ++ they are three buckets apart, and "this parser looped more than 128 times" becomes a feature worth keeping an input for.

Step two: the bucket and the counter index become a number

List 4.2 compiler-rt/lib/fuzzer/FuzzerTracePC.h:239 — CollectFeatures, the encoding lambda 
auto Handle8bitCounter = [&](size_t FirstFeature, size_t Idx, uint8_t Counter) {
  if (UseCounters)
    HandleFeature(static_cast<uint32_t>(FirstFeature + Idx * 8 + CounterToFeature(Counter)));
  else
    HandleFeature(static_cast<uint32_t>(FirstFeature + Idx));
};

So each counter byte owns eight consecutive feature numbers, one per bucket — which is why every region contributes 8 × size to the running FirstFeature offset. With -use_counters=0 a counter owns exactly one feature and the hit count is discarded.

Link in one more instrumented object — or load a second .ko whose harness grew a function — and FirstFeature shifts, so every extra-counter feature gets a new number. Two practical rules follow for Chapter 6: keep the harness binary's instrumented footprint stable across a campaign, and treat a corpus as paired with the binary that produced it — the same discipline you would apply to a profile-guided-optimization profile.

The stack-depth feature, which you are using without knowing it

§3.2's menu listed stack-depth; §3.3 never mentioned a consumer. There is one, and (on Linux) it is on by default — we saw that in §3.2's correction of what -fsanitize=fuzzer enables. The compiler maintains a thread-local low-water mark, the engine samples it per run:

That is why the mysterious TPC.RecordInitialStack() opens ExecuteCallback (§1.5): it resets the baseline so the mark measures this input's deepest call chain. An input that recurses deeper than anything before it earns a new feature and a corpus slot, even if it covered no new edge — which is how libFuzzer finds stack-exhaustion bugs that pure edge coverage is blind to. The step function is deliberately coarse (bands, not bytes) because an earlier, finer version "explod[ed] the corpus size" (f94d87aadf47, de891a19467d, 2017-12).

4.3 The corpus: ownership, eviction, and the energy schedule

§1.7 asserted that "selection is weighted, not uniform" and left it there. The weighting is about forty lines of FuzzerCorpus.h, and it is the part of libFuzzer most worth understanding before you tune anything.

Every feature has exactly one owner

List 4.4 compiler-rt/lib/fuzzer/FuzzerCorpus.h:419 — AddFeature — the smaller input takes ownership, and may evict the old owner 
bool AddFeature(size_t Idx, uint32_t NewSize, bool Shrink) {
  Idx = Idx % kFeatureSetSize;
  uint32_t OldSize = GetFeature(Idx);
  if (OldSize == 0 || (Shrink && OldSize > NewSize)) {   // unowned, or we are smaller
    if (OldSize > 0) {                                   // steal it from the old owner
      size_t OldIdx = SmallestElementPerFeature[Idx];
      InputInfo &II = *Inputs[OldIdx];
      II.NumFeatures--;
      if (II.NumFeatures == 0)
        DeleteInput(OldIdx);                            // it owned nothing: evict it
    } else {
      NumAddedFeatures++;
      if (Entropic.Enabled) AddRareFeature((uint32_t)Idx);
    }
    NumUpdatedFeatures++;
    SmallestElementPerFeature[Idx] = Inputs.size();      // the new owner
    InputSizesPerFeature[Idx] = NewSize;
    return true;
  }
  return false;
}

Three mechanisms you have already seen in the output log live in this one function. REDUCE is the Shrink branch: a smaller input that reaches a known feature takes ownership of it (Shrink is -reduce_inputs, default 1). Eviction is DeleteInput: an input whose last owned feature was stolen is dropped from the corpus and its file deleted — the corpus shrinks on its own, with no crash and no notice. And the ft: counter in the stat line is NumAddedFeatures, while the "did this run score?" subtraction of §1.6 reads NumUpdatedFeatures: the first counts features ever seen, the second counts ownership changes. That is why ft: can sit still while the engine is clearly busy.

Energy: how much mutation an input deserves

With -entropic=1 (the default since f3c2e0bcee64, 2020-09), each input carries a running estimate of how informative it is: the Shannon entropy of the frequencies of the features it hits. Rare features raise it; features everyone hits do not.

List 4.5 compiler-rt/lib/fuzzer/FuzzerCorpus.h:75 — UpdateEnergy (abridged) 
void UpdateEnergy(size_t GlobalNumberOfFeatures, bool ScalePerExecTime, ...) {
  Energy = 0.0;
  SumIncidence = 0;
  for (const auto &F : FeatureFreqs) {          // (feature, local hit count) pairs
    LocalIncidence = F.second;
    Energy -= LocalIncidence * log(LocalIncidence);   // Shannon term
    SumIncidence += LocalIncidence;
  }
  AbdIncidence = NumExecutedMutations + 1;      // add-one smoothing for the rest
  Energy -= AbdIncidence * log(AbdIncidence);
  SumIncidence += AbdIncidence;
  if (SumIncidence != 0)
    Energy = Energy / SumIncidence + log(SumIncidence);
  if (ScalePerExecTime)
    Energy *= PerfScore;                        // -entropic_scale_per_exec_time=1
}

Tracking frequencies for two million features would be absurd, so Entropic only tracks the rare ones: at most -entropic_number_of_rarest_features=100 of them, dropping the most abundant whenever a frequency climbs past -entropic_feature_frequency_threshold=0xFF (AddRareFeature, :365). Global counts live in a saturating uint16_t array (:448).

Now "weighted, not uniform" is concrete. ChooseUnitToMutate (:303) is one draw from that piecewise_constant_distribution. An input that owns no features has weight zero and is never picked again. An input fuzzed more than kMaxMutationFactor = 20× the corpus average is benched. And the fallback schedule — used before any energy exists — is weight = i + 1: strictly increasing with corpus index, so newer inputs are favoured simply for being newer, and a focus function multiplies by 1000.

Why this matters for a kernel harness. Three of these mechanisms assume features are stable and cheap. A KCOV harness violates all three mildly: PCs hashed into a small array collide (so "owning" a feature is fuzzier), each run costs a syscall (so -entropic_scale_per_exec_time=1 is worth trying), and a panic ends the campaign before the distribution has learned anything (§6.14). If your kernel corpus stops growing, check -print_corpus_stats=1: a corpus full of zero-weight inputs looks identical, from the outside, to a target with no reachable new coverage.

4.5 Crash-resistant campaigns: -fork and -merge

Everything so far ends with _Exit(). A campaign that must survive hundreds of findings therefore needs something outside the process, and libFuzzer has exactly one answer: -fork=N.

What the parent actually does

In fork mode the top-level process never calls your target. It builds command lines, spawns children, and merges what they bring back:

Three design choices are visible here. A child gets √N seeds, not the whole corpus, drawn skewed toward recent finds — small enough to start fast, biased toward the frontier. Job n runs for min(300, n) seconds, so early jobs are seconds long and later ones minutes: the campaign warms up. And -reload=0 plus a private corpus directory means children never see each other; all sharing happens through the parent's merge.

When a child exits — for any reason — the parent classifies it by exit code and merges its corpus:

The merge, and why it is crash-resistant

That CrashResistantMerge step is not a detail — it is how fork mode tolerates children that die mid-merge, and it is the same code behind plain -merge=1. The algorithm is documented in the header, and the control file is the entire trick:

List 4.11 compiler-rt/lib/fuzzer/FuzzerMerge.h:15 — the algorithm, in the authors' words 
//   The outer process collects the set of files and writes their names
//   into a temporary "control" file, then repeatedly launches the inner
//   process until all inputs are processed.
//   The outer process does not actually execute the target code.
//
//   The inner process reads the control file and sees a) list of all the inputs
//   and b) the last processed input. Then it starts processing the inputs one
//   by one. Before processing every input it writes one line to control file:
//   STARTED INPUT_ID INPUT_SIZE
//   After processing an input it writes the following lines:
//   FT INPUT_ID Feature1 Feature2 Feature3 ...
//   COV INPUT_ID Coverage1 Coverage2 Coverage3 ...
//   If a crash happens while processing an input the last line in the control
//   file will be "STARTED INPUT_ID" and so the next process will know
//   where to resume.
//
//   It uses a single pass greedy algorithm choosing first the smallest inputs
//   within the same size the inputs that have more new features.

A dangling STARTED line is the crash report: whatever input it names killed the previous attempt, so the next inner process skips past it. This is why -merge_control_file=PATH plus SIGUSR1 gives you a resumable corpus minimization (the recipe in the upstream docs), and why merging a corpus against a target that crashes on half of it still terminates.

And the limit you will hit in Chapter 6. Fork mode protects the fuzzer process. When the "crash" is a kernel panic, the guest — parent, children, control file and all — disappears together. -fork=1 buys nothing there; what replaces it is the reproducer-before-run discipline of §6.14, or moving the orchestration outside the VM entirely, which is what syzkaller does and what §9.5 reconsiders.

libFuzzer keeps whatever input reveals a new coverage feature and mutates it; the compiler's SanitizerCoverage pass is what makes features observable; and the __libfuzzer_extra_counters section is the escape hatch that lets code the compiler never touched — a rewritten binary, or a Linux kernel — pour its own coverage into the same loop. Around that loop sit the four subsystems of Chapter 4: a feature is a number on a shared number line (§4.2), a corpus is a map from each feature to its smallest owner (§4.3), a bug report is a global plus a signal handler (§4.4), and a campaign that survives its own findings is a parent process merging disposable children (§4.5). Every practical step in Part 2 is an application of exactly this.

Further exercises — think first, then open the answer

  1. Your LLVMFuzzerTestOneInput returns early for half of all inputs. Does libFuzzer still make progress on the rest — and what breaks if the early-return path leaves a global half-initialised?
    Answer
    Yes, the inputs that do reach instrumented code still generate features and drive the search. But because the run is in-process, any global mutated before the early return survives into the next input, so a later run can crash for reasons that have nothing to do with its own bytes — a non-reproducible "bug." The contract (§1.5) is: leave no persistent state across runs.
  2. A target hides a bug behind if (memcmp(data, "MAGIC", 5) == 0). Coverage alone never rewards getting 3 of 5 bytes right, yet libFuzzer cracks it in seconds. How — and which callback feeds which structure to make that possible?
    Answer
    The memcmp interceptor / __sanitizer_cov_trace_cmp* records the two operands into the TORC (table of recent compares). Mutate_AddWordFromTORC then splices the wanted operand "MAGIC" directly into the input, so the engine never needs partial-match coverage credit — it copies the answer in wholesale (§3.4).
  3. A Linux kernel is code libFuzzer's compiler pass never instrumented. Name the two pieces that still let it drive a coverage-guided search.
    Answer
    (1) KCOV instruments the kernel and records the PCs a task executes; (2) the harness folds those PCs into __libfuzzer_extra_counters, a section CollectFeatures reads exactly like compiler-emitted counters. The engine cannot tell donated coverage from its own (§2.2, and Chapter 6).
  4. libFuzzer schedules its mutators uniformly at random; a weighted version was added and then reverted. Argue why uniform is the right call for a coverage-guided fuzzer.
    Answer
    The feedback signal already concentrates effort: inputs that reveal features are saved and re-mutated, the rest die. A "smart" scheduler is a second, weaker optimizer that competes with that loop and overfits to past inputs; empirically it didn't help, so it was removed (§3.7). Intelligence belongs in selection, not in the dice.

Learning objectives (for a kernel driver developer)

  • Write the per-input KCOV loop correctly: enable → exercise driver → disable → marshal PCs into the counters array.

6.1 Two mechanisms: "automatic" vs "bring your own coverage"

Why the difference exists

In the userspace case (all of Chapter 1), the coverage plumbing is invisible. You never declare a counter array, never copy anything, never think about it — because the fuzzer, the instrumentation, and the target all live in one address space. The compiler emits inline counter writes directly into memory the engine already owns, and CollectFeatures reads them in place. Here is that baseline, the whole target, no coverage code anywhere:

List 6.1 compiler-rt/test/fuzzer/CounterTest.cpp — the "automatic" baseline 
extern "C" int LLVMFuzzerTestOneInput(const uint8_t *Data, size_t Size) {
  int Num = 0;
  for (size_t i = 0; i < Size; i++)
    if (Data[i] == 'A' + i) Num++;      // the compiler instruments this branch for you
  if (Num >= 4) { std::cerr << "BINGO!\n"; exit(1); }
  return 0;
}

A kernel driver breaks that assumption completely. The code you want to cover runs in ring 0, in a different address space, reached only across a system-call boundary. The compiler did instrument it (that is what CONFIG_KCOV is), but those counter writes land in kernel memory, not in your fuzzer. Nothing automatically bridges the gap. So the model inverts: you become responsible for collecting the signal on the far side and carrying it back. That carrying-back is what __libfuzzer_extra_counters is for.

KCOV in one page: the facility you are bridging to

Before the mechanics of moving coverage into libFuzzer, it helps to know exactly what is on the kernel side of the bridge. KCOV is the kernel's coverage collector, and — this is the neat part — it is built on the same SanitizerCoverage instrumentation the compiler inserts for userspace libFuzzer (Chapter 1 §1.9). Turn on CONFIG_KCOV and the kernel is compiled with -fsanitize-coverage=trace-pc; the callbacks are implemented not by libFuzzer's TracePC (Chapter 3 §3.3) but by the kernel itself, which writes into a per-task ring buffer that userspace can mmap. So "kernel coverage" is not a foreign concept — it is the coverage you already understand, produced on the far side of a syscall and handed back through a shared page.

Definition — KCOV. A per-task facility (CONFIG_KCOV, exposed at /sys/kernel/debug/kcov) that records the program counters of the basic blocks executed by the calling thread while enabled, into an mmap'd buffer shared with userspace. "Per-task" is the load-bearing word: it captures the thread that turned it on and nothing else — which is exactly why work that happens on a kworker needs the remote variant (§6.4c).

  ioctl(kcov, KCOV_INIT_TRACE, KCOV_COVER_SIZE);

  ioctl(kcov, KCOV_ENABLE, KCOV_TRACE_PC);          // record this thread's coverage
  return 0;
}

The ring-buffer format, and the per-run loop

The mapped buffer is dead simple: word 0 is a counter, and words 1..N are the recorded PCs. Every run you zero the counter, exercise the kernel, then read back however many PCs it recorded and fold them into the extra-counters array (§6.2). This is the same three-step "reset → run → collect" you saw in Chapter 1 §1.5's ExecuteCallback, but you are doing the plumbing by hand across the syscall boundary:

List 6.3 the per-run collection, from the reference harness — reset, run, fold every PC into a counter 
void kcov_start() { __atomic_store_n(&kcov_data[0], 0, __ATOMIC_RELAXED); }   // reset the counter

void kcov_stop() {
  unsigned long ncov = kcov_data[0];               // how many PCs were recorded
  for (unsigned long i = 0; i < ncov; i++) {
    unsigned long pc = kcov_data[i + 1];           // the i-th covered block PC
    libfuzzer_coverage[pc % sizeof(libfuzzer_coverage)]++;   // → an extra-counter feature
  }
}
// per input:  kcov_start();  ...drive the kernel via a syscall/ioctl...  kcov_stop();
Why pc % size? KCOV gives you absolute kernel addresses; the extra-counters array is a fixed hash table of hit counters. Reducing the PC modulo the array size spreads distinct blocks across the table (with occasional collisions) — the same trick the Cloudflare AFL shim used (Chapter 2 §2.3), and the reason §6.10 exists to turn those raw PCs back into source lines.

Two modes: block PCs, and comparison operands

KCOV_ENABLE takes a mode. KCOV_TRACE_PC (the default, mode 0) records block PCs, as above. KCOV_TRACE_CMP (mode 1, needs CONFIG_KCOV_ENABLE_COMPARISONS) instead records the operands of every comparison — the kernel's version of trace-cmp (Chapter 3 §3.3). That second mode is what lets a kernel harness recover the magic-value-cracking superpower by replaying the operands into libFuzzer's TORC, exactly as §6.4b does. Same facility, a different thing written into the same ring buffer.

The kernel you need, and where the reference lives

Minimally: CONFIG_KCOV=y and CONFIG_DEBUG_FS=y (for the /sys/kernel/debug/kcov node); add CONFIG_KCOV_ENABLE_COMPARISONS=y for the compare mode and CONFIG_KASAN=y for the bug oracle (Chapter 7). The authoritative reference is the kernel's own Documentation/dev-tools/kcov.rst, which carries a complete worked example; the ABI itself is 25 lines of include/uapi/linux/kcov.h. Note that the kernel ships no in-tree userspace harness — every project rolls its own, which is exactly contribution item K1 (§8.2). The recipe above is distilled from a KCOV+libFuzzer write-up (libfuzzer-kcov.md) and cross-checked against the lab harness in tools/harden/sample/local.c.

One more piece: stateful APIs need structure

Everything above delivers coverage. But most kernel attack surface is a stateful API — a sequence of syscalls or ioctls where each step depends on the last (you must open before you write). Feeding such an API a raw byte blob gets you nowhere. This is precisely the job for a custom mutator (Chapter 3 §3.8): the reference harness uses libprotobuf-mutator and the DEFINE_PROTO_FUZZER macro to mutate a typed message describing an API sequence, then serialises it into calls — structure-aware fuzzing, driven by KCOV coverage. Chapter 2 §2.4 walks that case study; the takeaway for here is that kernel-coverage integration and structure-aware input generation are two halves of the same harness.

Before wiring the kernel in, learn the array in isolation. This test is the canonical, authoritative example of the extra-counters contract, and its comments are the spec:

List 6.4 compiler-rt/test/fuzzer/TableLookupTest.cpp — the in-tree extra-counters example, with the rules in its own comment 
const size_t N = 1 << 12;

// Define an array of counters that will be understood by libFuzzer
// as extra coverage signal. The array must be:
//  * uint8_t
//  * in the section named __libfuzzer_extra_counters.
// Use either `Counters[Idx] = 1` or `Counters[Idx]++`
// depending on whether multiple occurrences of 'Idx' matter.
#if defined(__linux__) || defined(__FreeBSD__)
__attribute__((section("__libfuzzer_extra_counters")))
#endif
#ifdef _WIN32
#  pragma section(".data$__libfuzzer_extra_counters")

#endif

  if (Size != 4) return 0;
  uint32_t Idx; memcpy(&Idx, Data, 4); Idx %= N;
  assert(Counters[Idx] == 0);  // libFuzzer resets these between runs.
  Counters[Idx]++;
  ...
}

Four rules a kernel dev must internalize, each visible above:

  • Type and section are fixed. uint8_t, section __libfuzzer_extra_counters (or the .data$… Mach-O/COFF spelling). That name is the handshake with ExtraCountersBegin()/End() from §2.2; get it wrong and libFuzzer silently sees zero extra counters.
  • =1 vs ++ is your block-vs-edge-count choice. Setting to 1 records "this index was hit"; incrementing records "how many times," which libFuzzer buckets (1, 2, 3, 4–7, 8–15, …) into distinct features. For a driver, ++ lets loop trip-counts become new coverage.
  • libFuzzer zeroes the array before every run (the assert(Counters[Idx]==0) proves it — that is ClearExtraCounters() inside ResetMaps(), §3.3). Therefore you must re-fill it every single run — never accumulate across inputs.
  • You may declare more than one such array, and their sizes are up to you; they are all concatenated into the same section.
How you know it worked. The matching test file extra-counters.test checks for the banner INFO: N Extra Counters (emitted by PrintModuleInfo, §3.3) and that thousands of new_units_added appear. When you bring up your KCOV harness, that Extra Counters line at startup is your first confirmation the section is wired correctly — if it says 0 or is absent, your section(...) attribute or your build's dead-strip settings are wrong, and no kernel coverage will ever register.

6.4 Applying it to your driver: the KCOV recipe

Putting §6.2 and §6.3 together, here is the full shape of a KCOV libFuzzer harness. It is the out-of-process rig with the file transport replaced by the KCOV ring buffer. Set up once in the startup hook; marshal every run:

List 6.7 the KCOV harness skeleton (synthesised from libfuzzer-kcov.md and the in-tree rig) 
__attribute__((section("__libfuzzer_extra_counters")))
static uint8_t Counters[64 << 10];               // §6.2 rules apply

static unsigned long *KcovArea;   static int KcovFd;

extern "C" int LLVMFuzzerInitialize(int *argc, char ***argv) {     // §1.3 startup hook — once
  KcovFd = open("/sys/kernel/debug/kcov", O_RDWR);
  ioctl(KcovFd, KCOV_INIT_TRACE, KCOV_COVER_SIZE);          // _IOR('c', 1, unsigned long)
  KcovArea = mmap(NULL, KCOV_COVER_SIZE * sizeof(unsigned long),
                  PROT_READ|PROT_WRITE, MAP_SHARED, KcovFd, 0);
  return 0;
}

extern "C" int LLVMFuzzerTestOneInput(const uint8_t *Data, size_t Size) {
  __atomic_store_n(&KcovArea[0], 0, __ATOMIC_RELAXED);   // reset the kernel's counter
  ioctl(KcovFd, KCOV_ENABLE, KCOV_TRACE_PC);             // start recording THIS task

  drive_my_driver(Data, Size);                           // ← syscall/ioctl into your code

  ioctl(KcovFd, KCOV_DISABLE, 0);                        // stop recording
  unsigned long n = __atomic_load_n(&KcovArea[0], __ATOMIC_RELAXED);
  for (unsigned long i = 1; i <= n; i++)                 // marshal PCs → extra counters
    Counters[KcovArea[i] % sizeof(Counters)]++;          //   (the fread() of §6.3, by hand)
  return 0;
}

Four things a driver author must get right, beyond the §6.2 array rules:

(a) KCOV gives you blocks; edges need one more line

The raw ring buffer is a list of block PCs — that is block coverage (§2.6). To approximate edge coverage, apply AFL's prev_location trick from §2.3: hash consecutive pairs of PCs instead of single PCs.

List 6.8 turning KCOV's block PCs into edge features with AFL's prev_location trick 
uint32_t prev = 0;
for (unsigned long i = 1; i <= n; i++) {
  uint32_t cur = hash(KcovArea[i]);
  Counters[(cur ^ prev) % sizeof(Counters)]++;   // edge = (prev,cur) pair
  prev = cur >> 1;                                // asymmetry so A→B ≠ B→A
}

(b) The comparison signal is not free here — and how to get it back

This is the deepest "different mechanism" point. In userspace, trace-cmp (§3.3–§3.4) automatically fills TORC and the value profile, so magic-value checks fall for free. The extra-counters channel cannot carry operands — it is a byte array, and CollectFeatures only ever reads it as counters. So a naive KCOV harness loses the compare-solving superpower even if you enable KCOV_ENABLE_COMPARISONS.

The recovery is elegant and worth knowing: the trace-cmp callbacks in FuzzerTracePC.cpp are exported symbols (ATTRIBUTE_INTERFACE, §3.3). KCOV's comparison mode hands you (type, arg1, arg2, pc) tuples; you can replay each one into libFuzzer's own TORC by calling the callback yourself, during the run:

List 6.9 replaying KCOV comparison tuples into libFuzzer's TORC by calling the callback yourself 
// with KCOV in KCOV_TRACE_CMP mode, for each recorded (arg1, arg2):
extern "C" void __sanitizer_cov_trace_cmp8(uint64_t, uint64_t);
...
__sanitizer_cov_trace_cmp8(arg1, arg2);   // feeds TORC + value profile (§3.3) as if in-process

This must happen while RunningUserCallback is true (i.e. inside LLVMFuzzerTestOneInput), because §3.3's weak hooks are gated on it. Done right, the mutator's Mutate_AddWordFromTORC (§3.4) will splice kernel-observed constants into your inputs — closing the same loop for a kernel that §3.4 closed for userspace. This is morally what syzkaller does with KCOV comparison feedback.

(c) Determinism and state

§1.1's rules still bind, but a kernel makes them harder: leftover descriptors, sockets, or allocations from one run perturb the next, turning the coverage signal into noise. For stateful drivers use the fork()-per-input pattern from §2.5 so the OS reclaims resources between iterations.

(d) A crash must reach the harness as a signal

A KASAN report in dmesg is invisible to libFuzzer (§1.5, §2.4). Either scrape /dev/kmsg and abort the harness on a new report, or apply the §2.4 kernel patch that turns a KASAN hit into a SIGSEGV delivered to the offending task. Without this, libFuzzer will happily mutate away the very input that found your bug.

Pitfalls checklist (in bring-up order)

  1. Section name. Confirm the startup banner prints INFO: N Extra Counters with N > 0. If not, your section("__libfuzzer_extra_counters") spelling or a dead-strip pass is at fault (§6.2). Nothing else can work until this does.
  2. Re-fill every run. Never rely on values persisting; libFuzzer zeroed the array (§6.2). Equally, zero the kernel's KcovArea[0] yourself each run (§6.4).
  3. Enable KCOV on the right task. KCOV is per-task; enable/disable must bracket the code path on the same thread that enters the kernel. Work done by a kernel workqueue or softirq will not be recorded — a known KCOV limitation.
  4. Block vs edge. If coverage plateaus fast, you are probably feeding block PCs; switch to the consecutive-pair hash (§6.4a).
  5. Compare feedback. If the fuzzer stalls on a magic constant or a header field, enable KCOV_ENABLE_COMPARISONS and replay operands into the trace-cmp callbacks (§6.4b) rather than hoping the counter channel carries them — it cannot.
  6. Crashes. Verify a deliberately buggy input actually stops the fuzzer and writes a crash-* file. If a KASAN splat scrolls by in dmesg but the fuzzer keeps going, wire up the signal path (§6.4d).
  7. State bleed. If replaying a saved crash-* file does not reproduce, suspect cross-run kernel state; add the fork() isolation (§6.4c / §2.5).

6.7 Warm-up: a write-side bug behind layered guards

Start in pure userspace — no kernel, no KCOV — to see the coverage-vs-random point cleanly. tools/harden/userspace/userspace.c parses an 8-byte header and only reaches a heap-overflow write when four conditions line up: a 4-byte magic "HARD", a version, a kind byte, and an attacker-claimed length larger than the real payload:

List 6.10 tools/harden/userspace/userspace.c — four guards in front of a heap-overflow write 
if (memcmp(h.magic, "HARD", 4) != 0) return 0;   // ~1 in 2^32 by luck
if (h.version != 2) return 0;
if (h.kind != 0x7) return 0;
uint8_t *buf = malloc(payload_len ? payload_len : 1);
if (h.len > payload_len)
    memcpy(buf, payload, h.len);                  // <-- heap-buffer-overflow WRITE

Tested result. Built with the project's clang and run for a few seconds, libFuzzer finds it essentially instantly — the trace-cmp → TORC → mutation loop (Chapter 3 §3.4) splices "HARD" in at once, then climbs the remaining guards:

List 6.11 the recipe that works, and the reproducer it produced 
$ clang -g -O0 -fsanitize=fuzzer,address userspace.c -o userspace
$ ./userspace -max_total_time=30
...
==ERROR: AddressSanitizer: heap-buffer-overflow ... WRITE of size ...
Test unit written to ./crash-1b9ddb52...
0x48,0x41,0x52,0x44,0x2,0x7,0xfe,0xff,            "HARD" + ver 2 + kind 7 + len 0xfffe
A real gotcha worth its own paragraph: optimization can erase your coverage. At -O1/-O2 this exact target compiles to a binary libFuzzer reports as 1 inline 8-bit counter — the optimizer merges all four guard blocks into one region, so there is no per-guard gradient and the fuzzer runs blind (it never solves the magic in 20M runs). At -O0 the CFG stays 1:1 with the source (10 counters) and the bug falls in seconds. This is the compiler-vs-coverage interaction from Chapter 3 §3.2 made painfully concrete: coverage instrumentation is inserted late, and aggressive block-merging upstream can starve it. For tiny teaching targets, prefer -O0; for real targets, keep functions non-trivial (or use __attribute__((noinline)) on the guarded work) so the gradient survives.

The Rust twin (userspace.rs) is identical in logic and built with cargo-fuzz; it uses an explicit copy_nonoverlapping so the fault is a genuine OOB write (a safe buf[..n].copy_from_slice would instead abort with a bounds-check panic — also a finding, but not a memory-safety one).

6.8 The kernel target: a zero-copy driver with a planted bug

Now the real thing. samples/harden/local.c is a misc device that allocates one page at open and co-maps it into userspace with remap_pfn_range — the exact same physical page the kernel later reads (zero copy, no copy_from_user). On ioctl(HARDEN_RUN) it walks the page in 8-byte commands. Two opcodes write to a tiny kmalloc'd array; only one of them bounds-checks the index:

List 6.12 samples/harden/local.c — the planted bug (KASAN catches it) 
case OP_SET:                       /* SAFE path */
    if (idx < HARDEN_SLOTS)
        d->slots[idx] = val;
    break;
case OP_SET_RAW:                   /* the BUG: no bounds check, behind a flag */
    if (flag == HARDEN_RAW_MAGIC)
        d->slots[idx] = val;       /* <-- slab-out-of-bounds WRITE when idx >= 16 */
    break;

The buggy branch needs op == OP_SET_RAW and flag == 0xA5 and idx >= 16 to line up — the same "funnel" idea as the userspace warm-up, now inside the kernel. A blind fuzzer rarely lands all three; a KCOV-guided one climbs to it. remote.c is byte-for-byte the same parser, but runs it on a workqueue kthread so the coverage must be collected with the remote API.

This is the kind of detail that only surfaces when you try to reproduce someone else's lab, which is why the script is in the tree rather than in this paragraph.

CONFIG_KASAN_GENERIC=y is the oracle that turns the driver's out-of-bounds write into a report. But turning that report into something the fuzzer can observe (the reporting bridge, §7.3) has a subtlety the lab surfaced empirically: CONFIG_PANIC_ON_OOPS=y is not enough — a KASAN report is not an "oops", so with only panic_on_oops the kernel logs BUG: KASAN: … and keeps going, and the fuzzer runs right past the bug. The bridge that actually works is the boot parameter kasan.fault=panic, which lab.sh passes on the guest command line (§6.10). With it, the first KASAN hit panics the VM and the fuzzer process dies with it — the crash is captured. This is precisely the "make the kernel tell the fuzzer" problem of Chapter 7 §7.3, and the answer is a boot flag, not just a config.

A real hardening-build gotcha worth its own paragraph: KASAN vs. the frame-size limit. The first build attempts died not in the samples but in core kernel files (lib/maple_tree.c, fs/coredump.c) with error: stack frame size exceeds limit (2048) [-Werror,-Wframe-larger-than]. Cause: a KASAN build adds redzones that inflate stack frames past CONFIG_FRAME_WARN=2048, and CONFIG_WERROR=y makes the warning fatal. The two config lines that fix it are in the script above: (1) CONFIG_KASAN_STACK=n — the per-variable stack redzones are the worst offender, and our injected bug is a heap slab-overflow, so stack instrumentation buys us nothing here; and (2) CONFIG_FRAME_WARN=4096 — raise the threshold so the frames that remain (from heap KASAN + the deep maple-tree/coredump paths) no longer trip -Werror. Raising FRAME_WARN sticks through vng's olddefconfig where trying to disable it outright (=0) or turn off WERROR did not. This is exactly the friction Chapter 7 warned about: a hardened (sanitizer-heavy) build is not free — you pay for the oracle in build-config effort.

6.12 Symbolizing coverage under KASLR (and module load bases)

KCOV hands you raw runtime program counters. The moment you want to turn one — a coverage PC, or the address in a KASAN report — back into a file:line, you hit KASLR: the kernel is loaded at a randomized base each boot, so a runtime PC does not match the link-time address in vmlinux. And there is a second, subtler base: our buggy code lives in a module (harden_run in harden_local.ko), and modules are loaded at a dynamically allocated address whether or not KASLR is on. So symbolizing module coverage always needs the module's load base.

First, the reassuring part: fuzzing doesn't care. Coverage guidance only needs PCs that are distinct and stable within one boot — which they are — so libFuzzer hashes them into the extra-counters array (§6.4) and steers perfectly well with KASLR on. Address translation matters only when a human wants to read a PC. And for the crash specifically, you rarely need any math: KASAN already prints a symbol+offset, e.g. BUG: KASAN: slab-out-of-bounds in harden_run+0x2a/0x120 [harden_local] — that +0x2a is module-relative and directly usable.

Where the arithmetic is needed is turning a raw KCOV coverage PC into source. There are two bases to know, depending on which code the PC belongs to:

Table 6.6 Which base a raw KCOV program counter needs, where to read that base, and which tool symbolizes the result.
PC belongs to…Its baseHow to get the baseSymbolize with
kernel core (vmlinux) kernel KASLR slide dmesg | grep 'Kernel Offset', or runtime(sym) − static(sym) addr2line -e vmlinux $((pc − slide))
a module (our case) module .text load address (dynamic; independent of KASLR) /sys/module/<mod>/sections/.text (needs kptr_restrict=0) addr2line -e <mod>.ko $((pc − base))

Under the hood: the kernel functions that place — and measure — these addresses

The recipe above is four shell commands, but a beginner should see where in the kernel those numbers come from. It reduces to three questions: who moves the kernel, how does the kernel know by how much, and why is a module different? Each has a short, readable answer in the source of the very kernel this lab boots.

1. Who moves the kernel: base KASLR and one anchor address

The linker fixes every kernel symbol relative to a single compile-time anchor. On x86-64 that anchor is __START_KERNEL_map:

List 6.20 arch/x86/include/asm/page_64_types.h:46 — __START_KERNEL_map, the compile-time base every slide is measured against 
#define __START_KERNEL_map  _AC(0xffffffff80000000, UL)

So at build time the first byte of kernel text, the symbol _text, is placed a fixed distance above that anchor (call the link-time value __START_KERNEL, roughly 0xffffffff81000000). At boot, when CONFIG_RANDOMIZE_BASE (KASLR) is on, the decompressor picks a random slide and copies the whole kernel image up by that amount — so every symbol's runtime address is its link-time address plus the same slide. Passing nokaslr simply forces that slide to zero.

2. How the kernel measures its own slide: kaslr_offset()

The kernel exposes the exact slide as a one-line inline function — and it is the whole idea in a single subtraction:

List 6.21 arch/x86/include/asm/setup.h:100 — kaslr_offset(): the slide is one subtraction 
static inline unsigned long kaslr_offset(void)
{
        return (unsigned long)&_text - __START_KERNEL;
}

Read it slowly. &_text is the runtime address of the _text symbol — and because the kernel is already running at its slid location, that address already includes the slide. __START_KERNEL is where the linker placed _text at build time. Subtract the two and everything cancels except the random slide. That returned value is precisely the Kernel Offset: 0x… line the boot log prints, and precisely what you must subtract from a core-kernel PC before addr2line.

Worked example — a core-kernel PC

  1. KCOV hands you a coverage PC in built-in code: pc = 0xffffffff83a014f0.
  2. The kernel's slide is kaslr_offset() = 0x2000000 (from dmesg | grep 'Kernel Offset').
  3. Link-time address = pc − slide = 0xffffffff81a014f0.
  4. addr2line -e vmlinux 0xffffffff81a014f0 → file:line. Done.
You can recompute kaslr_offset() without being in the kernel. Both operands are visible from userspace: the runtime _text lives in /proc/kallsyms, the link-time _text (or _stext) in System.map. Their difference is the slide — which is exactly the _stext subtraction shown in "If you must keep KASLR on" below. The kernel and your shell are computing the same number two ways.

Beginner aside: KASAN turns off one flavour of KASLR

This lab builds with KASAN, and the kernel deliberately disables memory-region randomization when KASAN is enabled:

List 6.22 arch/x86/include/asm/setup.h — kaslr_memory_enabled() — KASAN silently disables memory randomisation 
static inline bool kaslr_memory_enabled(void)
{
        return kaslr_enabled() && !IS_ENABLED(CONFIG_KASAN);
}

Note what this does not cover: it gates only the randomized placement of the big virtual regions (the direct map, vmalloc, vmemmap) — which KASAN pins because its shadow mapping must stay PGD-aligned. The kernel base slide from step 1 is independent and can still be non-zero unless you pass nokaslr. The lab passes nokaslr, so for us the base slide is zero too, and the only moving target left is the module base — next.

3. Why a module has its own base: it is allocated, not linked in

Built-in code lives inside vmlinux and rides the single kernel slide. A loadable module is different: at insmod time the loader asks the executable-memory allocator for a fresh chunk of the module address window:

List 6.23 kernel/module/main.c:1352 — module_memory_alloc() — a fresh .text address on every load 
execmem_type = EXECMEM_MODULE_TEXT;
ptr = execmem_alloc_rw(execmem_type, size);   /* a fresh .text address, every load */

That address is carved from the module window [MODULES_VADDR, MODULES_END) (arch/x86/include/asm/pgtable_64_types.h: MODULES_VADDR = __START_KERNEL_map + KERNEL_IMAGE_SIZE). Because it is allocated at load time rather than fixed by the linker, it lands somewhere new on every insmod — with or without KASLR. That is the second base in the table above, and the reason our recipe reads it at runtime instead of hard-coding it.

4. How /sys/module/…/sections/.text hands you that base — and why it can read as zero

When you cat /sys/module/harden_local/sections/.text, the number is produced by this read handler:

List 6.24 kernel/module/sysfs.c — the sections/.text read handler 
wrote = scnprintf(bounce, sizeof(bounce), "0x%px\n",
                  kallsyms_show_value(file->f_cred)
                        ? battr->private : NULL);

Two details every beginner trips on. battr->private is the section's real load address — the module base we want. But it is only printed when kallsyms_show_value(file->f_cred) is true; otherwise the handler substitutes NULL, so an under-privileged reader gets 0x0000000000000000. That single conditional is the source-level reason the recipe first runs sysctl -w kernel.kptr_restrict=0: without it the base reads back as all-zeros and every subtraction silently produces nonsense. (The same kallsyms_show_value gate is why kernel pointers appear hashed in reports read from an unprivileged context.)

Who prints harden_run+0x2a in the crash? The same kallsyms machinery, from the other direction: the in-kernel symbolizer (kallsyms_lookup(), used by the oops/KASAN printer) walks the loaded modules, finds which one owns the faulting PC, subtracts that module's base for you, and prints symbol+offset [module]. That is why the crash line needs no arithmetic (§6.12 opening) — the kernel already did the exact subtraction from step 4 internally. You only do it by hand for raw KCOV coverage PCs, which are never symbolized for you.

The lab's approach: nokaslr + the module base

lab.sh makes this painless. It boots with --append nokaslr (so any vmlinux PC equals its link-time address) and, after loading the module, drops kernel.kptr_restrict and prints the module's .text base:

List 6.25 what lab.sh printed in the actual run (§6.10) 
sysctl -w kernel.kptr_restrict=0
insmod samples/harden/harden_local.ko
cat /sys/module/harden_local/sections/.text     # 0xffffffffc0400000 — the real module base

With that base in hand, a raw coverage PC your harness collected becomes source in two steps — subtract the base, then addr2line against the .ko:

List 6.26 a module PC to a source line — subtract the load base, then addr2line 
base=0xffffffffc0400000                                # from /sys/module/.../sections/.text
pc=0xffffffffc04004f6                                  # a raw PC from the KCOV buffer
llvm-addr2line -f -e samples/harden/harden_local.ko $(( pc - base ))   # 0x4f6
#   -> harden_run     (the injected OOB write, samples/harden/local.c:111)
The crash needs no math. The KASAN report from the run already reads slab-out-of-bounds in harden_run+0x2b6/0x350 [harden_local] — a symbol+offset the kernel resolved for you. The base-subtraction dance above is only for turning raw KCOV coverage PCs (absolute addresses in the ring buffer) into source; the KASAN crash line is already human-readable. (With this module's debug info, addr2line resolves to the function harden_run; the offending statement is the unchecked d->slots[idx] = val at local.c:111.)
Why nokaslr isn't enough for modules. nokaslr pins only the kernel base. Loadable modules are vmalloc'd at load time, so harden_local.ko still lands at a fresh .text address on every insmod. That is why the recipe reads /sys/module/.../sections/.text at runtime rather than assuming a fixed address — and why kptr_restrict=0 (which unmasks kernel pointers in /sys and /proc/kallsyms) is a prerequisite.

If you must keep KASLR on

Leave nokaslr off and recover the kernel slide explicitly. The kernel logs it at boot, or you compute it from any symbol:

List 6.27 recovering the KASLR slide, from the boot log or from any symbol 
# slide from the boot log:
dmesg | grep -i 'Kernel Offset'
#   Kernel Offset: 0x1e000000 from 0xffffffff81000000 (relocation range: ...)

# or from a symbol, static vs. runtime:
slide=$(( 0x$(grep ' T _stext$' /proc/kallsyms | cut -d' ' -f1) \
        - 0x$(grep ' T _stext$' System.map      | cut -d' ' -f1) ))
addr2line -e vmlinux $(( vmlinux_pc - slide ))    # for CORE-kernel PCs only

Module PCs are unaffected by this slide — keep using the per-module .text base above. In short: one base for vmlinux (the KASLR slide, or zero under nokaslr), and a separate base per loaded module (always dynamic). Our lab's bug is in a module, so the module base is the one that matters.

§6.12 grounding: /sys/module/<name>/sections/.text and kernel.kptr_restrict are standard kernel interfaces; lab.sh boots with nokaslr and prints the module base after insmod. The "Kernel Offset" boot line requires CONFIG_RANDOMIZE_BASE=y (KASLR) to be meaningful; under nokaslr the slide is zero.

6.13 Reading the ASAN/KASAN report, lab by lab

Every lab in §6.10 ends the same way: the fuzzer trips the planted bug and a sanitizer report scrolls out. That report is not noise to skim past — it is the oracle's testimony (§6.1, Chapter 7), the one artifact that tells you what broke, where, and how. This section re-runs all five labs and reads their real reports line by line. The reports below are verbatim from an actual run of this lab (addresses and PIDs will differ on yours); nothing is invented.

ASAN and KASAN are siblings. The userspace warm-up uses AddressSanitizer (ASAN); the kernel labs use Kernel Address Sanitizer (KASAN). They are the same idea in two habitats: a shadow memory that marks every byte as addressable or poisoned, checked on each access. So once you can read one report, you can read them all — which is exactly why we read five. The repetition is the point: the same skeleton appears each time, and seeing it five times with different flesh is how it becomes second nature.

The anatomy of a sanitizer report (the skeleton you'll see five times).
  1. The verdict — the bug class and the faulting function: ERROR: AddressSanitizer: <class> or BUG: KASAN: <class> in <func>+off.
  2. The access — Write/Read of size N at addr …, and crucially which task did it.
  3. Where in your code — the call stack; the top frame is your function at file:line.
  4. The memory's life story — allocated by (and, for a use-after-free, Freed by).
  5. The proof — the spatial/temporal detail: N bytes after a M-byte region, the slab cache, and the shadow bytes.
  6. The aftermath — how the run stops: libFuzzer writes a crash-<sha1> and prints stats (userspace); the kernel panics and our harness saves the reproducer (kernel, §6.14).

Lab 1 — userspace warm-up (ASAN)

bash lab.sh userspace. No VM: plain libFuzzer + ASAN on the host. Here is the tail of a real run:

Every report names the fault as function+0xoffset, not file:line. Closing that last gap is a two-tool skill — one tool per habitat, the same three questions each time: which source line?, which inlined callers?, and which machine instruction? Do it once per lab and the reports stop being opaque.

The workflow, in one line each

  • Userspace (ASAN): re-run with ASAN_OPTIONS=symbolize=0 to get raw binary+0xoff, then addr2line each offset (and objdump -S for the instruction).

6.14 Capturing the reproducer under a panicking kernel

The reporting bridge from §6.9 has a cost. When kasan.fault=panic fires, the whole VM goes down — and with it the fuzzer process, before libFuzzer can write its usual crash-<sha1> artifact. So the panic tells you a bug exists and names the function, but the exact input that triggered it is gone. For a lab whose whole point is to study the finding, we want that input back.

The idea. Have the harness persist each trial input to a host file just before handing it to the kernel. virtme's --rw flag makes the host filesystem write-through, so a file written (and fsync'd) from the guest survives the guest's death. After the panic, that file holds the last input tried — which is exactly the one that crashed.
List 6.39 tools/harden/sample/local.c — the reproducer write, before the ioctl 
if (repro_fd >= 0) {                    // HARDEN_REPRO=<host path>
    lseek(repro_fd, 0, SEEK_SET);
    if (ftruncate(repro_fd, 0) == 0 && write(repro_fd, data, n) >= 0)
        fsync(repro_fd);               // durable on the host BEFORE the crashing ioctl
}
memcpy((void *)shared, data, n);
ioctl(dev_fd, HARDEN_RUN);              // may panic — but the input is already saved
The overhead is real, and it forces a design choice. That fsync is not free: every input now makes a synchronous round-trip across 9p to the host, which measured at ~350 exec/s versus ~100,000 without it — a ~250× slowdown. (Dropping the fsync restores speed but loses the input: virtme's 9p is cached, so an un-synced write is discarded when the guest dies.) In a real campaign you would never log every input like this; you would use the §2.4 KASAN→signal bridge so libFuzzer saves the reproducer in-process. But for this practice we want to review the reproducer, so the lab keeps the durable log and pays for it — and buys the speed back a different way (next paragraph). This trade-off — durable logging vs. throughput — is itself a worthwhile thing to have felt.

Buying back the speed with a seed corpus. At 350 exec/s the fuzzer would take minutes to rediscover the bug from an empty corpus, so lab.sh seeds the corpus with a near-miss input — one that already reaches the buggy branch but with a safe index:

List 6.40 seeds/harden.seed — a near-miss input that reaches the buggy branch with a safe index 
# seeds/harden.seed:  count=1 ; op=OP_SET_RAW(2)  idx=0 (SAFE)  flag=0xA5  val=1
01 00 00 00 00 00 00 00  02 00 a5 01 00 00 00 00

From there the fuzzer only has to mutate one byte — the index — out of range, so the crash and its saved reproducer appear in seconds even with the reproducer log on. A seed corpus is standard practice: it bootstraps structure the fuzzer would otherwise brute-force; the crash still requires the fuzzer to drive the index out of bounds.

Reading the captured reproducer — and a real subtlety it reveals. After a run the file on the host decodes straight back to the crashing command:

List 6.41 the captured reproducer, decoded straight back into the crashing command 
$ xxd tools/harden/repro-harden_local.bin
0100 0000 0000 0000  0236 a501 0000 0000
#          count=1 ; op=2 (OP_SET_RAW)  idx=0x36=54 (>=16 → OOB)  flag=0xA5  val=1
Why the Rust driver sometimes reports slab-use-after-free and the C one slab-out-of-bounds — and why it is neither a Rust nor a KASAN bug. The reproducer's index byte is the whole story. Both drivers do the identical unbounded write slots[idx] = val (idx is a byte, 0–255) past a 16-byte heap object. Correlating the captured index with the KASAN class across runs:
  • C, idx = 17 → slab-out-of-bounds
  • Rust, idx = 16 → slab-out-of-bounds
  • Rust, idx = 128 → slab-use-after-free
A small over-index lands in the object's redzone → KASAN calls it out-of-bounds; a large one lands far past the object in memory that belonged to a since-freed object → KASAN calls it use-after-free. The same Rust code produced both, depending only on the index the fuzzer happened to pick and the runtime slab layout. So the earlier C-vs-Rust difference was heap-layout luck, not a language or toolchain difference: KASAN correctly reports whatever the first out-of-range byte belongs to. (If you wanted a deterministically-OOB demo, mask the index to a small over-range so it always hits the redzone.)

The HARDEN_CMP=1 mode does exactly that. It puts KCOV in KCOV_TRACE_CMP mode (enabled by CONFIG_KCOV_ENABLE_COMPARISONS=y in lab.sh build), and for each recorded compare it calls libFuzzer's own exported callback:

List 6.42 tools/harden/sample/local.c — the replay loop (§3.3's callbacks, driven by the kernel) 
// each KCOV_TRACE_CMP record is {type, arg1, arg2, pc}
for (each record) {
    switch (1u << ((type & KCOV_CMP_MASK) >> 1)) {   // operand size in bytes
    case 1: __sanitizer_cov_trace_cmp1((uint8_t)a1,  (uint8_t)a2);  break;
    case 2: __sanitizer_cov_trace_cmp2((uint16_t)a1, (uint16_t)a2); break;
    case 4: __sanitizer_cov_trace_cmp4((uint32_t)a1, (uint32_t)a2); break;
    default:__sanitizer_cov_trace_cmp8(a1, a2);                     break;
    }
    bump(pc);                                          // compare-site PC as coverage
}

Those callbacks are the very ones from Chapter 3 §3.3; calling them feeds the kernel's compare operands into libFuzzer's Table Of Recent Compares, so the mutator can splice a kernel-observed constant (like our flag == 0xA5) straight into the input. It is the §6.4b technique made concrete: the compiler emitted the compare instrumentation into the kernel, KCOV shipped the operands across the syscall boundary, and the harness hands them to the same TORC that in-process fuzzing fills automatically.

The honest trade-off. A single per-task KCOV instance can be in either PC mode or CMP mode, not both — so HARDEN_CMP=1 trades full edge coverage for compare-site coverage plus operand replay. For a target gated by a hard magic-value check it is a clear win; for our deliberately-easy bug (found fast either way once seeded) it is a demonstration of the mechanism rather than a necessity. The lesson matches §6.4b: compare feedback across the KCOV boundary is possible, but you assemble it by hand from exported pieces, and it is not free.

Chapter 7

Security hardening: turning latent bugs into observable crashes

A recurring thread through this whole study — §1.5's crash-on-signal contract, §2.4's KASAN→SIGSEGV patch, §6.4d's crash-detection pitfall — is that coverage tells the fuzzer where to go, but something else must tell it when it has arrived at a bug. That "something else" is a bug oracle. Security hardening, in a fuzzing context, is mostly the craft of installing oracles that convert a silent, latent fault into a loud, observable crash. This part is the guide to that stack for a kernel target.

Learning objectives

  • Separate the two jobs a fuzzing build must do — guidance (coverage) and detection (oracles) — and explain why coverage alone finds nothing.
  • Choose the right sanitizer for a bug class (spatial, temporal, uninit, race, UB) and know their mutual (in)compatibilities.
  • Build the reporting bridge that makes a kernel fault reach libFuzzer as a signal.
  • Add amplifiers (fault injection, lockdep, poisoning) that expose bugs a single happy-path run would miss.

7.1 The oracle principle: a fuzzer finds only what it can see

Definition — bug oracle. A mechanism that decides an execution has violated a correctness or safety property and signals it in a way the fuzzer can observe (a crash, an abort(), a delivered signal). Without an oracle a fuzzer maximises coverage over code that may already be corrupting memory — it will "successfully" execute the bug and move on. Every hardening option below is, from the fuzzer's point of view, an oracle.

7.2 The sanitizer & hardening stack

The kernel offers a layered set of oracles. A serious fuzzing build turns on as many as are mutually compatible; the config fragment in libfuzzer-kcov.md is essentially this table made concrete. Group them by the bug class each one catches:

Table 7.1 The kernel's oracles by CONFIG_ symbol: the bug class each turns into a crash, and what it costs a fuzzing build.
Oracle (CONFIG_*)Bug class it turns into a crashNotes for a fuzzing build
KASAN (KASAN, KASAN_INLINE) heap/stack/global out-of-bounds, use-after-free (spatial + temporal) the single highest-value oracle for drivers; KASAN_INLINE is faster than outline. HW_TAGS (arm64 MTE) is the low-overhead production variant.
KMSAN uninitialized-memory reads (incl. info leaks to userspace) Clang-only; heavy; mutually exclusive with KASAN in one build — run as a separate campaign.

You cannot stack everything at once. KASAN and KMSAN cannot coexist in a single kernel; both are expensive. The practical answer is campaigns: one long KASAN+UBSAN build (the default workhorse), a separate KMSAN build for info-leaks, a KCSAN build with a concurrent harness for races. Each campaign is the same coverage-guided loop with a different oracle bolted on — which is exactly why keeping guidance (KCOV) and detection (the sanitizer) decoupled, as this document has stressed, pays off operationally.

7.3 The reporting bridge, amplifiers, and a hardening checklist

The reporting bridge — make the kernel tell the fuzzer

An oracle that only prints is useless to an in-process userspace harness (§1.5, §2.4): libFuzzer never reads dmesg. You must build a bridge so a kernel report becomes a fuzzer-visible event. There are three standard techniques, in increasing robustness:

Table 7.2 Three ways to bridge a kernel report into a fuzzer-visible event, in increasing order of robustness.
TechniqueMechanismTrade-off
Panic-on-report sysctl kernel.panic_on_warn=1, panic_on_oops=1; run the kernel in a VM (KVM/virtme) so a panic just kills the guest simplest and catches everything, but ends the VM — best with fork/snapshot or out-of-process orchestration; one bug per boot.
Scrape /dev/kmsg harness watches the kernel log for a new BUG:/KASAN: line and abort()s itself keeps the VM alive across the crash but is racy and log-format-dependent (the Cloudflare post's approach).
Signal-on-report patch KASAN's print_error_description() to send_sig_info(SIGSEGV, …, current) — the guilty task takes the signal synchronously (§2.4) most precise: the crash lands inside ExecuteCallback on the exact input; requires a kernel patch and panic_on_warn=0.

Amplifiers — expose bugs a happy-path run would miss

Coverage plus an oracle still only finds a bug on inputs that reach it. Two amplifier families widen what "reach" means:

  • Fault injection (FAULT_INJECTION, FAILSLAB, FAIL_PAGE_ALLOC, FAIL_MAKE_REQUEST, …): synthetically fail allocations and I/O so the fuzzer explores error-handling paths — historically the richest seam of kernel bugs, because cleanup code is under-tested. Drive the probability via debugfs from the harness.
  • Liveness watchdogs (DETECT_HUNG_TASK, soft/hard LOCKUP_DETECTOR, WQ_WATCHDOG, RCU_CPU_STALL_TIMEOUT): turn hangs and livelocks — which a plain fuzzer would just time out on — into explicit, attributable reports. Tune the timeouts down for a fast fuzzing loop (DEFAULT_HUNG_TASK_TIMEOUT, RCU_CPU_STALL_TIMEOUT).
Determinism is a security property here too. §1.1 and §6.4c warned that cross-run state poisons the coverage signal; it also poisons the oracle. A use-after-free that only triggers because the previous input left a dangling pointer is real, but it is unreproducible and un-triageable if every run inherits arbitrary state. fork() isolation (§2.5) and disabling RANDOMIZE_BASE (KASLR) for stable PCs are as much about making bugs actionable as about finding them.

Hardening checklist for a kernel fuzzing build

  1. Guidance: KCOV on (selectively, per Chapter 2), KCOV_ENABLE_COMPARISONS if you want compare feedback (§6.4b).
  2. Primary oracle: KASAN + KASAN_INLINE, plus UBSAN. This is the default workhorse build.
  3. Reporting bridge: pick one of §7.3 — panic_on_warn in a VM, kmsg scraping, or the KASAN→signal patch. Verify a known-buggy input actually stops the fuzzer.
  4. Hardening oracles: FORTIFY_SOURCE, HARDENED_USERCOPY, LOCKDEP/PROVE_LOCKING, PROVE_RCU, DEBUG_VM.
  5. Amplifiers: fault injection (FAILSLAB et al.) and the hung-task / lockup / WQ watchdogs, with fuzzing-tuned timeouts.
  6. Determinism: fork() isolation for stateful drivers; disable RANDOMIZE_BASE; set panic_on_oops consistently with your bridge choice.
  7. Separate campaigns: a distinct KMSAN build (info leaks) and a concurrent-harness KCSAN build (races) — they cannot share the KASAN build.

Chapter 7 grounding: the config set is drawn from libfuzzer-kcov.md's kernel scripts/config fragment and cross-checked against the reporting mechanics in §1.5/§2.4; sanitizer bug-class assignments follow the upstream kernel dev-tools documentation. Exact CONFIG_* availability varies by kernel version — verify against your tree.

L1 · Implement Darwin extra counters

How it works today. L2 · Finish const_cmp instrumentation

How it works today. When one operand of a comparison is a compile-time constant, the compiler emits __sanitizer_cov_trace_const_cmp* instead of the plain trace_cmp*. But libFuzzer's handler for the const variant is a byte-for-byte copy of the non-const one — both just call HandleCmp — with an in-code TODO admitting the missed opportunity:

List 8.2 compiler-rt/lib/fuzzer/FuzzerTracePC.cpp:467 — trace_const_cmp8 throws away the fact that one operand is a constant 
// "...should be changed later to make full use of instrumentation."
void __sanitizer_cov_trace_const_cmp8(uint64_t Arg1, uint64_t Arg2) {
  uintptr_t PC = reinterpret_cast<uintptr_t>(GET_CALLER_PC());
  fuzzer::TPC.HandleCmp(PC, Arg1, Arg2);   // identical to trace_cmp8

Why it's useful. A constant operand is strictly more information than a runtime-vs-runtime compare: it is a known target value the input must eventually match. It deserves a stronger, more permanent dictionary/value-profile weighting than the ephemeral TORC entry a normal compare gets (§3.3). Realising that distinction is a concrete way to crack magic-value checks faster.

Items L5 and K5 are the same project seen from two sides, and they are the through-line of the work this study grew out of. Be precise about status, because it is the kind of thing a reader will check: the compiler side is an open pull request (llvm/llvm-project#201410) that emits __sanitizer_cov_trace_args / __sanitizer_cov_trace_ret — including struct-field layouts via DICompositeType and an FNV-1a name hash. The kernel side is an out-of-tree patch series (kernel/kcov_dataflow.c, a kcov_dataflow uAPI header, Documentation/dev-tools/kcov_dataflow.rst and six selftests) which does consume them. Neither is merged. So of the two consumers the diagram below names, one is written and awaiting review, and one — the libFuzzer mutator — is still nobody's patch (§3.3).

That diagram is the natural place to end the study, because it recapitulates its whole thesis. The compiler's job is to emit a signal and nothing more; the signal is meaningless until a consumer gives it meaning; and the same emitted callback can feed a kernel coverage subsystem and an in-process fuzzing engine, exactly as the counter arrays of Chapters 1–6 fed both SanitizerCoverage and KCOV. A contributor who implements either consumer is doing, at the frontier, precisely what HandleCmp (§3.3) and Mutate_AddWordFromTORC (§3.4) already do for comparisons — closing a new dataflow loop from the compiler, through the runtime, back into the inputs.

A thin AFL-style layer: packaging the harness into a custom fuzzer

By §6.4 you had already written a working kernel fuzzer by hand: an __libfuzzer_extra_counters array, a KCOV setup, a per-input fold loop, a compare replay. This chapter does the obvious next thing — lifts that boilerplate into a small library so a new target costs three calls — and, along the way, answers the question the whole book has been circling: if libFuzzer can do all this, what exactly does AFL give you that libFuzzer doesn't? The honest answer is ergonomics, and ergonomics you can rebuild.

9.1 AFL's conveniences are policies, not powers

A recurring question from readers who reach the end of Chapter 6: we just fed kernel coverage into libFuzzer and replayed kernel compares into its mutator — so why do so many kernel-fuzzing write-ups reach for AFL instead? The answer is not that AFL can see something libFuzzer can't. It is that AFL ships a handful of default policies that happen to match the awkward shape of an out-of-process, crash-prone target — and libFuzzer, being an in-process engine first, leaves those policies for you to assemble. Assemble them once, behind a thin layer, and the convenience gap closes.

Thin layer. A small amount of glue — a header, a linker flag, a couple of runtime calls — that re-creates another tool's ergonomics on top of an engine's existing primitives, without touching the engine. It changes what the harness author has to type, not what the fuzzer can do.

Draw the line cleanly. On one side, the things AFL genuinely is: an evolutionary loop, a coverage bitmap, a mutation scheduler. libFuzzer has all three (Chapters 1–3) — different implementations, same capabilities. On the other side, the things AFL defaults to: a fork server so a crash never kills the master, a @@ convention so an unmodified file-reading program is a valid target, a persistent/deferred mode so expensive setup runs once, cmplog so magic values fall. Each of those is a policy, and §9.2 shows the libFuzzer primitive that implements it.

The one honest exception. AFL's mutation schedule — the deterministic bit-flip walk, then havoc, then splice — is a different strategy, not just a different default (§3.7 contrasts it with libFuzzer's MutateDepth chain). A thin layer will not give you that; replacing the schedule is a custom mutator job (§3.8), a deeper change. Everything else in this chapter is glue.

9.3 libbyoc: bring-your-own-coverage in one small header

The §6.4 harness mixed three concerns in one file: KCOV bookkeeping, the edge fold, and your driver logic. Split the first two into a library and the driver author is left with only the third. The public surface is three calls:

List 9.1 libbyoc.h — the whole public interface 
/* Bring-your-own-coverage for libFuzzer. Three calls, no engine changes. */
int  byoc_init(const char *dev);   /* open driver + KCOV, install extra counters (§1.3 hook) */
void byoc_begin(void);             /* reset + KCOV_ENABLE — call first in TestOneInput      */
void byoc_end(void);               /* KCOV_DISABLE, fold PCs to edges, replay compares      */

extern int byoc_dev_fd;            /* the driver fd, for your one ioctl */

The implementation is nothing more than §6.4 with the boilerplate named and hidden. Note it is the library that now owns the __libfuzzer_extra_counters array — the §6.2 rules (single definition, fixed size, non-zero counts) are satisfied once, here, for every target that links it.

List 9.2 libbyoc.c — §6.4a (edge fold) + §6.4b (compare replay), packaged 
#define BYOC_MAP (64 << 10)
__attribute__((section("__libfuzzer_extra_counters")))
static uint8_t  byoc_cov[BYOC_MAP];          /* the AFL-style bitmap (§2.2) */

static uint64_t *area;   static int kfd;   int byoc_dev_fd = -1;

int byoc_init(const char *dev) {
  byoc_dev_fd = open(dev, O_RDWR);
  kfd = open("/sys/kernel/debug/kcov", O_RDWR);
  ioctl(kfd, KCOV_INIT_TRACE64, KCOV_COVER_SIZE);
  area = mmap(NULL, KCOV_COVER_SIZE*8, PROT_READ|PROT_WRITE, MAP_SHARED, kfd, 0);
  return (byoc_dev_fd >= 0 && area != MAP_FAILED) ? 0 : -1;
}

void byoc_begin(void) {
  __atomic_store_n(&area[0], 0, __ATOMIC_RELAXED);   /* reset kernel cursor */
  ioctl(kfd, KCOV_ENABLE, KCOV_TRACE_PC);            /* record THIS task    */
}

void byoc_end(void) {
  ioctl(kfd, KCOV_DISABLE, 0);
  uint64_t n = __atomic_load_n(&area[0], __ATOMIC_RELAXED), prev = 0;
  for (uint64_t i = 1; i <= n; i++) {                /* §6.4a: block PCs → edges */
    uint64_t cur = area[i] * 0x9e3779b1u;
    byoc_cov[(cur ^ prev) % BYOC_MAP]++;
    prev = cur >> 1;                                  /*   asymmetry: A→B ≠ B→A */
  }
}

With that in place, a whole kernel-fuzzing harness for the lab's driver is what remains after the plumbing is gone — the three calls, plus your single ioctl:

List 9.3 harness.c — everything target-specific, and nothing else 
#include "libbyoc.h"

int LLVMFuzzerInitialize(int *argc, char ***argv) {
  return byoc_init("/dev/harden_local");            /* §1.3 — once */
}

int LLVMFuzzerTestOneInput(const uint8_t *data, size_t size) {
  byoc_begin();
  ioctl(byoc_dev_fd, HARDEN_RUN, &(struct run){ data, size });   /* your driver */
  byoc_end();
  return 0;
}

That is the payoff. The next driver — a different /dev node, a different ioctl — changes exactly two lines. The coverage path, the bitmap, the edge fold, the §6.2 rules: all amortised into libbyoc.

Compare mode is one flag. For the §6.4b compare-replay variant, have byoc_begin() pass KCOV_TRACE_CMP and have byoc_end() walk the buffer as {type, arg1, arg2, pc} 4-tuples, calling __sanitizer_cov_trace_cmp8(arg1, arg2) for each inside the run so §3.3's hooks are live. The harness above does not change — the library absorbs the difference. This is the thin-layer principle in miniature: policy moves into the glue, the target stays still.

9.4 Keeping an existing main(): LLVMFuzzerRunDriver + --wrap=main

AFL's most-loved convenience is the @@ target: point it at a program that already takes a file on the command line, and you are fuzzing — no harness, no rewrite. libFuzzer looks like the opposite: it owns main, so "my program already has a main" feels like a wall. It isn't. libFuzzer exposes its driver as an ordinary function, LLVMFuzzerRunDriver(), and the linker's --wrap lets you slip in front of the existing main without editing it.

List 9.4 glue.c — fuzz an unmodified file-reading program 
extern "C" int LLVMFuzzerRunDriver(int *argc, char ***argv,
                                   int (*cb)(const uint8_t *, size_t));
extern int __real_main(int argc, char **argv);      /* the program's own main */

/* The target: run the input through the SAME code path main() uses. */
extern "C" int LLVMFuzzerTestOneInput(const uint8_t *data, size_t size) {
  parse_buffer(data, size);   /* the function main() reaches after reading its file */
  return 0;
}

/* --wrap=main renames the real main to __real_main and routes calls here. */
extern "C" int __wrap_main(int argc, char **argv) {
  if (getenv("FUZZ"))
    return LLVMFuzzerRunDriver(&argc, &argv, LLVMFuzzerTestOneInput);
  return __real_main(argc, argv);                   /* untouched normal behavior */
}

Link with clang -fsanitize=fuzzer-no-link ... -Wl,--wrap=main -lFuzzer. Now one binary has two personalities: run it normally and it is the original file tool; run it with FUZZ=1 and libFuzzer drives LLVMFuzzerTestOneInput at full in-process speed. That is precisely AFL's @@ convenience — "fuzz the program I already have" — expressed with libFuzzer's own driver entry point, and it composes with §9.3: the parse_buffer body can just as well be byoc_begin(); ioctl(...); byoc_end(); to drive a kernel instead of userspace code.

Why --wrap and not just a fresh main? Because the existing program may depend on its own main for the non-fuzz path (a real CLI, a test suite). Wrapping keeps that path byte-for-byte intact and adds the fuzz path beside it, so the same source ships both ways — the deferred-forkserver spirit of "one binary, two entry modes."

9.5 Crash survival and compare replay: -fork=1 and cmplog for free

Two conveniences remain, and both are already in libFuzzer — you just have to know the flag.

Fork survival. AFL's fork server exists so a crashing input kills a child, not the campaign. libFuzzer's -fork=1 is the same idea: the master hands batches to short-lived worker processes; when a worker dies on a crash, the master records the reproducer and spawns a fresh one. Add -ignore_crashes=1 and a run keeps going through hundreds of distinct faults, exactly like an AFL campaign.

List 9.5 fork mode as an AFL-style fork server — one flag, two caveats 
./harness -fork=1 -ignore_crashes=1 -jobs=8 corpus/
The kernel caveat you cannot flag away. -fork=1 protects the fuzzer process. It does nothing when the crash is a kernel panic that tears down the whole guest — the master dies with the VM. This is the real reason out-of-process kernel rigs feel more natural, and it is exactly why §6.14's reproducer-before-run pattern (write and fsync the input before the ioctl) is non-negotiable for the in-process kernel harness. The thin layer closes the ergonomics gap for userspace and for survivable driver faults; for a panicking guest, the §6.14 discipline is the substitute for a fork server, not -fork=1.

Compare solving (cmplog). There is nothing left to build: §6.4b already replays kernel comparison operands into __sanitizer_cov_trace_cmp*, and §9.3's compare-mode byoc_end() folds it into the library. For a userspace target it is even simpler — compile with -fsanitize-coverage=trace-cmp and libFuzzer fills TORC itself (§3.3–§3.4). AFL bolts cmplog on as a second instrumented binary; here it is one compiler flag or one library mode.

Step back and the picture is complete. Five AFL conveniences, five libFuzzer primitives, one small layer of glue — and the result is a fuzzer with libFuzzer's in-process engine, TORC, and value profile, wearing AFL's ergonomics. What you have not replaced is the mutation schedule (§3.7); if a target genuinely wants AFL's deterministic-then-havoc walk, that is the custom-mutator frontier of §3.8, and a fair next project. Everything short of that, you can now assemble yourself.

From a byte array to a kernel crash, and out to the frontier

You took the loop from Part 1 and made it drive real kernel code: KCOV donates coverage, KASAN supplies the oracle, virtme-ng gives a disposable target, and KASLR arithmetic turns a raw PC back into a line of source. The gaps Chapter 8 catalogues — a stubbed Darwin file, a callback with no consumer — are where this study stops being reading and starts being a patch; and Chapter 9 shows that the harness you wrote by hand is, with a little glue, a reusable custom fuzzer that wears AFL's ergonomics over libFuzzer's engine.

Further exercises — think first, then open the answer

  1. Your harness enables KCOV, calls the driver's ioctl, and reads 0 PCs every time — yet the driver clearly ran. Most likely cause, and the fix?
    Answer
    The driver's work runs on a different task than the one that called KCOV_ENABLE (a workqueue kthread), and local KCOV only records the enabling task. Fix: remote coverage — kcov_remote_start(handle) inside the kthread, with the harness installing that common handle via KCOV_REMOTE_ENABLE (§6.4c, and the Rust remote.rs).
  2. A KASAN report scrolls past in dmesg, but libFuzzer keeps going and never saves the crashing input. Why — and what, in spirit, is the one-line fix?
    Answer
    A KASAN report alone doesn't hand the fuzzer a signal it can see. You need the reporting bridge: make the fault fatal and observable — kasan.fault=panic plus capture, or bridge the report to a delivered signal — so coverage's guidance is matched by an oracle's detection (§7.1, §7.3). Without it, the fuzzer guides but "finds" nothing.
  3. KASLR is on. A report shows 0xffffffffc0a01234, but addr2line on the .ko yields garbage. What must you subtract first?
    Answer
    The module load base. Read /sys/module/<name>/sections/.text, subtract it from the PC to get a file-relative offset, then addr2line against the unstripped .ko (for in-vmlinux code, subtract the kernel .text base derived from _stext instead) — §6.12.
  4. trace-args/trace-ret are emitted by the compiler but have no libFuzzer consumer. Sketch a minimal useful consumer — and the risk that keeps it out of tree.
    Answer
    Feed captured argument/return values into the value profile / TORC (as HandleCmp does), so the mutator can inject observed constants — turning dataflow into guidance. The risk is volume: every call logs values, which can flood features and dilute the signal, so it needs sampling/filtering. That is exactly why it is non-trivial and belongs on-list first (§8.3).
End matter

Epilogue

The claim in the preface was that libFuzzer's coverage input is a byte array and the engine cannot tell who filled it in. Here is what that bought, stated as an accounting. The engine dissected in Chapter 1 ran against a Linux kernel driver in Chapter 6 unmodified: not a patched libFuzzer, not a fork, the libclang_rt.fuzzer that ships. What we wrote instead was a harness — four ioctls to arm KCOV, a loop to fold its ring buffer into a counter array, and the driver call in between. The engine saw features arriving and did what it always does. It never learned that the code producing them was in another privilege level.

That is the whole trick, and it generalises past the kernel. Any producer of execution traces — a binary rewriter, an emulator, a hypervisor, a microcontroller reporting over a serial line — can be wired to the same seam, because the seam asks for nothing but bytes. The reason Chapter 2's three authors arrived at it independently is that there is only one door.

The lesson that cost the most to learn

If you retain one structural idea from Part 2, make it the one drawn in Figure 7.1: guidance and detection are separate subsystems, and a bug needs both to fire on the same input. Coverage tells the fuzzer where to go. A sanitizer tells it that something broke. Neither implies the other, and almost every kernel-fuzzing attempt that quietly fails has exactly one of them.

A harness with immaculate KCOV plumbing and no oracle will run for a week, report rising feature counts, and find nothing — it is corrupting memory happily and silently. KASAN without coverage is a random walk that happens to be instrumented. The two halves are built by different people, enabled by different configuration, and debugged by different techniques, which is why Chapter 6 and Chapter 7 are separate chapters and why the lab turns on both before it claims anything.

What is still open

Chapter 8 is a list of gaps, and it is the part of this book most likely to stop being true. Three of them are worth restating, because they are of genuinely different kinds:

  • Mechanical. FuzzerExtraCountersDarwin.cpp returns nullptr, so extra counters — the seam this entire book is about — simply do not work on macOS. In-tree prior art for the fix exists in the Windows sibling. Someone with a Mac and an afternoon could close it.
  • Small and real. __sanitizer_cov_trace_const_cmp8 discards the one thing that distinguishes it from trace_cmp8: the knowledge that an operand is a compile-time constant. The source says so, in a comment, and has said so for years.
  • Genuinely open. trace-args/trace-ret is a compiler signal with no customer on either side of the boundary — nothing emits it in the checkout this book was verified against, and nothing would consume it if it did. That is the joint frontier of §8.3, and the obstacle is not plumbing but volume: every call logs values, and a feature set can be drowned as easily as it can be starved.

On the kernel side the shape of the problem is different, and more political than technical. KASAN's end_report() can panic the machine or do nothing; there is no path that delivers a signal to the task that caused the fault. Every reporting bridge in Chapter 7 exists to route around that single absence. A patch there is not hard to write and not obviously right to apply, which is precisely why kernel items in this book say propose it on-list first rather than send the patch.

Why the gaps are the ending

A book that only explains cannot be checked. The chapters that name a file and say “this is unimplemented” can be falsified by anybody with a checkout and ten minutes — and eventually will be, by somebody fixing them. That is the intended ending, and it is a better one than a summary.

As for the engine: libFuzzer will probably not grow another subsystem. It is therefore a stable thing to study and a cautious thing to depend on, and those two facts are not in tension. What transfers out of these 191 pages is not the engine but the shape of it — instrument, execute, score, select, mutate — and that shape is what Centipede, AFL++, syzkaller and whatever comes next are all implementations of. Having read one of them line by line, you will recognise the others on sight, and you will know which of their claims to check first.

The next step is not another chapter. Clone the tree, build the lab, break the driver, read the report, and then go and fix one of the files in Chapter 8.
